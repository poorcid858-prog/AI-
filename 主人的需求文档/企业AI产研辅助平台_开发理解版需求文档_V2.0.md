## 一、项目定位

本平台是一套面向企业内部产品、研发、测试等角色的 AI 辅助平台。

**核心目标：**
1. 提升产品、研发、测试的工作效率
2. 沉淀企业内部知识
3. 将 AI 能力组件化、复用化
4. 对 AI 输出质量进行审核和持续优化

平台不是简单的 AI 聊天工具，而是将企业知识、AI 能力、业务流程和大模型组合起来形成完整的企业 AI 应用。

## 四、AI 工作台

**定位：** 最终用户的主要使用入口。用户不需要了解 RAG、Skill、Workflow、Prompt、Reference 等底层概念，主要通过自然语言表达需求。

| 功能 | 说明 |
|------|------|
| **产品助手** | 需求分析、PRD 生成、需求优化、业务方案设计、产品文档生成 |
| **测试助手** | 测试用例生成、测试场景分析、异常场景补充、测试文档生成 |
| **前端助手** | 页面代码生成、组件代码生成、代码解释、代码优化 |
| **AI 对话** | 支持自然语言交流 |
| **历史记录** | 保存历史 AI 任务和对话结果 |

**意图识别：**
- 默认情况下用户不需要手动选择"需求分析""PRD 生成"等任务类型
- 系统通过 LLM 进行语义理解，判断任务类型并路由到对应 Workflow
- 若置信度较低，再通过澄清问题让用户选择

**设计原则：** AI 工作台以自然语言为主要入口，不强制用户先选择任务分类。

## 五、知识中心

**定位：** 负责管理企业知识资产，为 AI 提供企业内部事实知识。

**知识处理流程：**

```
原始文档 → 文档解析 → 标准化处理 → 分类/打标签 → Chunk 切分 → 向量化 → 向量数据库 → RAG 检索 → 返回相关知识
```

**文档与 Chunk 采用父子关系。** 例如：

```
会员积分规则 V3.0
├── Chunk 001：积分有效期
├── Chunk 002：积分获取规则
├── Chunk 003：积分兑换规则
└── Chunk 004：积分失效规则
```

**Chunk 建议保存字段：**
`chunk_id`、`document_id`、`content`、`sequence`、`business_line`、`knowledge_type`、`applicable_role`、`applicable_scene`、`version`、`permission`、`status`、`embedding`

元数据用于检索过滤、权限控制、知识治理和场景匹配。

## 六、RAG 的作用和介入时机

RAG 不是固定属于 Skill。RAG 是一种知识获取能力，Workflow 根据具体任务判断是否调用 RAG。

**例如：**
> 用户：帮我生成会员积分兑换优惠券 PRD
> → 意图识别
> → PRD 生成 Workflow
> → RAG 检索会员积分规则、会员等级规则、历史 PRD
> → PRD Skill
> → Reference
> → Prompt
> → LLM

**推荐关系：**
```
Workflow
├── RAG 检索
└── Skill
```

这样 RAG 可以被不同 Workflow 复用。

## 七、能力中心

**定位：** 用于创建、配置、测试、发布和管理 AI 能力。**能力中心是后台配置工具，不是前台用户直接使用的入口**——用户在 AI 工作台使用 AI，能力中心负责把"AI 能做什么"配置出来。

**核心产出物：** 以 **AI 能力** 为单位的对象（如"PRD 生成能力""测试用例生成能力"）。一个 AI 能力是面向用户的**业务能力**。

### 新增 AI 能力的流程

新建 AI 能力时，核心操作是**选择 Workflow**：

```
新增 AI 能力
    ↓
选择能力覆盖的岗位（如产品经理、测试工程师、前端工程师等）
    ↓
选择或配置 Workflow
    ├── 选择已有的 Workflow → 该 Workflow 已经包含了 Skill / Reference / Prompt / Tool / Script 等要素
    └── 新建 Workflow → 需要配置对应的要素
    ↓
配置其他关联信息（如 RAG 知识源等）
    ↓
测试 → 审核 → 发布
    ↓
展示在能力列表
```

**关键理解：** Workflow 不是"空壳"，它本身已经包含了 Skill、Reference、Prompt、Script、Tool 这些要素。新增 AI 能力时，核心是**选择 Workflow**（已有的或新建的），选好 Workflow 就确定了这个能力包含什么。

### 能力列表（能力聚合视图）

能力中心必须提供一个**以 AI 能力为单位的列表**，集中管理所有已创建的能力。每条能力展示其关联的 Workflow，以及该 Workflow 包含的所有要素：

```
能力列表
├── PRD 生成能力
│   ├── 覆盖岗位：产品经理
│   ├── Workflow: PRD 生成 Workflow
│   │   ├── Skill: 需求分析 Skill
│   │   ├── Reference: PRD 模板 V2
│   │   ├── Prompt: 全局系统 Prompt
│   │   ├── Tool/Script: （无）
│   │   └── RAG 知识源: 会员积分规则
│   ├── 状态：已发布（v3）
│   └── 创建时间：2026-08-15
├── 测试用例生成能力
│   ├── 覆盖岗位：测试工程师
│   ├── Workflow: 测试用例 Workflow
│   │   ├── Skill: 测试设计 Skill
│   │   ├── Reference: 测试规范
│   │   ├── Prompt: 测试角色 Prompt
│   │   ├── Tool/Script: Markdown 格式转换
│   │   └── RAG 知识源: 订单系统文档
│   ├── 状态：待审核
│   └── 创建时间：2026-08-14
└── ...
```

即：能力列表提供能力维度的**聚合视图**，一条能力能看到它关联的 Workflow，以及该 Workflow 包含的全部要素（Skill / Reference / Prompt / Tool / Script / RAG 知识源），以及状态、版本、覆盖岗位等信息。

### AI 能力与 Workflow 的关系

- AI 能力是最终面向用户的业务能力
- Workflow 是这个 AI 能力背后的执行流程
- **Workflow 已经包含了 Skill、Reference、Prompt、Script、Tool 等要素**，所以选择 Workflow 就等于确定了能力的技能组合
- 用户看到的是"需求分析助手"（能力），而不是具体 Workflow 或底层要素

### 能力与 AI 工作台、提问模板的关系

- **能力中心与 AI 工作台没有前端视觉上的联动。** AI 能力新增/发布后是**系统层面**的感知——系统知道"我有这个能力"，但不会自动在 AI 工作台 UI 上出现对应的入口。
- **如果希望某个能力能在聊天页被用户使用，需要人工配置一个提问模板**。例如：新增了"PRD 生成能力"后，管理员在提问模板配置页添加一条"PRD 生成"模板，用户在聊天页点击该模板即触发对应能力。
- 即：**能力发布 ≠ 自动出现在工作台**；能力到工作台的桥梁是**人去配提问模板**，配的时候选择关联哪个能力。

## 八、Workflow

Workflow 负责组织和控制整个 AI 任务如何执行。

**典型流程：**
```
开始 → 需求理解 → RAG 检索 → Skill 调用 → Reference 加载
→ Prompt 组装 → LLM → 结果检查 → 结束
```

**Workflow 可以配置：**
- 节点
- 节点顺序
- 条件判断
- 调用的 Skill
- RAG 知识源
- Reference
- Prompt
- Tool / Script
- 使用模型

## 九、Skill

**定位：** 负责完成一个具体的专业任务。

**例如：**
- 需求分析 Skill
- PRD 生成 Skill
- 测试用例生成 Skill
- 代码生成 Skill

**Skill 配置内容：**
- Skill 名称
- Skill 描述
- 所属业务线
- 适用场景
- 输入参数及说明
- 能力规则
- 执行规则
- 约束条件
- 输出格式
- 输出字段
- 关联 Prompt

**示例：**
| 属性 | 内容 |
|------|------|
| **Skill 名称** | 需求分析 Skill |
| **输入** | 用户需求 |
| **执行规则** | 分析用户目标、识别业务流程、拆解功能、识别异常场景 |
| **输出** | 需求分析结果 |

## 十、Reference

Reference 负责提供企业标准、模板、案例和参考内容。

**例如：**
- 公司 PRD 模板
- 优秀 PRD 案例
- 测试规范
- 产品设计规范
- 优秀输出示例

**RAG 与 Reference 的区别：**

| 概念 | 作用 |
|------|------|
| **RAG** | 企业事实知识 |
| **Reference** | 企业标准、模板、案例 |

简单理解：RAG 告诉 AI"事实是什么"，Reference 告诉 AI"应该参考什么标准完成"。

---

## 十一、Prompt

Prompt 采用分层设计：

```
全局 Prompt
↓
角色 Prompt
↓
Workflow Prompt
↓
Skill Prompt
↓
用户输入
```

同时可以将 RAG 检索结果、Reference 内容作为上下文加入最终 Prompt。

**最终模型输入可理解为：**
```
全局规则 + 角色规则 + Workflow 规则 + Skill 规则 + Reference + RAG 知识 + 用户需求
```

## 十二、Tool 和 Script

**Tool** 解决 AI 需要调用外部系统或外部能力的问题，例如会员系统查询、订单查询、数据库查询、代码检查。

**Tool 典型配置：**
Tool 名称、Tool 描述、输入参数、API/接口、参数规则、返回结果、权限

**Script** 解决 AI 需要执行确定性的程序逻辑，例如 Markdown 转 Word、文件格式转换、数据清洗、Excel 生成。

**Script 典型配置：**
Script 名称、输入参数、执行逻辑、输出结果、运行环境、超时设置

**简单区分：** Tool 偏"调用外部能力"，Script 偏"执行固定程序"。

**负责：**

## 十四、运营与管理中心

主要解决：AI 运行得怎么样？

**使用分析：**
- 用户数
- 使用次数
- 助手使用情况
- AI 能力调用情况

**效果分析：**
- 用户满意度
- 点赞 / 点踩
- 任务完成情况
- 结果采纳情况

**问题定位：**
分析一次 AI 任务完整执行链路：
```
用户输入 → 意图识别 → Workflow → RAG → 召回 Chunk → Skill → Reference → Prompt → LLM → 最终输出
```

## 十五、系统管理

系统管理负责平台本身的基础配置，而不是 AI 业务运营。

| 功能 | 说明 |
|------|------|
| **用户 / 角色** | 管理用户、角色及用户与角色关系 |
| **权限** | 控制谁能使用 AI 工作台、管理知识、配置 Workflow、管理 Skill、配置模型等 |
| **模型配置** | 统一管理平台可使用的模型，包括模型名称、模型类型、API 地址、API Key、Temperature、Token 限制、启用状态等 |
| **AI 日志** | 记录 Request ID、用户、时间、模型、Token、耗时、状态、错误信息等 |
| **系统配置** | 管理平台级参数 |

**模型配置与能力中心的关系：**
- 系统管理负责"有哪些模型可以用"
- 能力中心的 Workflow 负责"这个能力使用哪个已经配置好的模型"

---

## 十六、运营中心与系统管理的区别

| 维度 | 运营与管理中心 | 系统管理 |
|------|---------------|---------|
| **关注点** | AI 业务运行怎么样 | 系统本身怎么运行 |
| **示例** | 产品助手使用次数、满意度、Workflow 失败率、RAG 召回情况 | 模型 API 是否可用、用户权限是否正确、系统参数是否正确 |

## 十七、AI 问题定位机制

每次 AI 请求都应保留完整执行链路：

```
Request ID
├── 用户输入
├── 意图识别结果
├── Workflow
├── RAG
│   ├── 查询
│   ├── 召回 Chunk
│   └── 召回分数
├── Skill
├── Reference
├── Prompt 版本
├── Model
└── 最终输出
```

**例如：** 用户反馈"AI 回答不准确"，管理员可以检查：
```
意图识别 → Workflow → RAG → Skill → Reference → Prompt → LLM
```

如果发现 RAG 没有召回正确知识，则可定位为知识召回问题，而不是简单归因于大模型。

## 二十、开发时必须遵守的关键规则

1. 用户默认通过自然语言使用 AI，不强制选择任务类型。
2. AI 能力不是 Workflow 本身，Workflow 是 AI 能力背后的执行流程。
3. RAG 不是 Skill 的固定子步骤，而是 Workflow 可以调用的知识获取能力。
4. 知识中心负责知识资产管理，RAG 负责运行时知识检索。
5. Skill 负责专业任务能力，不等于 Prompt。
6. Reference 负责模板、规范、案例，不等于 RAG。
7. Tool 负责外部系统调用，Script 负责确定性的程序执行。
8. Chunk 属于文档的子级数据，必须保留 document_id 父子关系。
9. Prompt 采用分层设计。
10. 每次 AI 执行必须记录完整执行链路，支持问题定位。
11. 普通用户不能修改 Workflow、Skill、Prompt 等 AI 能力配置。
12. 能力必须经过测试、审核、发布后才能正式被 AI 工作台调用。
13. 系统管理负责平台基础配置，运营中心负责 AI 业务效果分析。
14. 模型统一在系统管理中配置，Workflow 只引用已经配置好的模型。
15. 不要把 RAG、Skill、Reference、Workflow 等底层概念直接暴露给普通用户。

## 二十二、开发建议

**建议开发顺序：**

1. 建立整体项目框架
2. 用户、角色、权限
3. AI 工作台
4. 知识中心
5. 能力中心
6. 审核中心
7. 运营与管理中心
8. 系统管理
9. 打通完整 AI 运行链路

**开发前优先定义对象模型和对象之间的关系，再设计页面和交互**，避免只完成页面而没有真正的数据和业务关联。
