## 一、先把整个系统的对象关系定死

这是代码 AI 最需要理解的。

```
                    ┌──────────────┐
                    │   AI 工作台    │
                    │  用户使用入口  │
                    └──────┬───────┘
                           │
                           ↓
                     用户自然语言
                           │
                           ↓
                    ┌──────────────┐
                    │   意图识别    │
                    │ LLM 理解任务   │
                    └──────┬───────┘
                           │
                           ↓
                    ┌──────────────┐
                    │   Workflow   │
                    │ 组织执行流程  │
                    └──────┬───────┘
                           │
          ┌────────────────┼────────────────┐
          ↓                ↓                ↓
       RAG 检索          Skill 调用        Tool/Script
          │                │                │
          ↓                ↓                ↓
      知识中心          能力中心          外部能力
          │                │
          └────────┬───────┘
                   ↓
              Reference
                   ↓
             Prompt 组装
                   ↓
                  LLM
                   ↓
                输出结果
```

**重要关系：**
- 知识中心负责"存知识"
- 能力中心负责"怎么使用这些知识和能力"
- 不要让代码 AI 把 RAG 直接做成一个"知识库页面上的按钮"就结束了

## 二、最容易理解错的：能力中心

能力中心不是简单的"几个列表"，它实际上是**创建 AI 能力的地方**。

例如：现在公司没有"需求分析"能力，管理员进入能力中心：

```
新建 AI 能力
      ↓
选择能力覆盖的岗位（如产品经理、测试工程师等）
      ↓
选择或配置 Workflow
      ├── 选择已有的 Workflow → 该 Workflow 已包含 Skill / Reference / Prompt / Tool / Script 等要素
      └── 新建 Workflow → 需要配置对应的要素
      ↓
配置其他关联信息（如 RAG 知识源等）
      ↓
测试
      ↓
发布
      ↓
展示在能力列表
```

**关键理解：** 新增 AI 能力时，核心是**选择 Workflow**（已有的或新建的）。Workflow 不是空壳，它本身已经包含了 Skill、Reference、Prompt、Script、Tool 这些要素。选好 Workflow 就确定了这个能力包含什么。

建议页面结构明确成：

```
能力中心
├── AI 能力
│   ├── PRD 生成能力（覆盖岗位：产品经理）
│   │   └── Workflow: PRD 生成 Workflow
│   │       ├── Skill
│   │       ├── Reference
│   │       ├── Prompt
│   │       ├── Tool / Script
│   │       └── RAG 知识源
│   └── 测试用例生成能力（覆盖岗位：测试工程师）
│       └── Workflow: 测试用例 Workflow
│           └── ...
├── Workflow
├── Skill
├── Reference
├── Prompt
└── Tool / Script
```

## 三、AI 能力和 Workflow 是什么关系？

**定义：**
- **AI 能力**是最终可以被用户调用的业务能力
- **Workflow**是这个 AI 能力背后的执行流程

**例如：**

```
AI 能力：需求分析助手
        ↓
Workflow：需求分析 Workflow
        ↓
┌───────────────────┐
│ 1. 需求理解        │
│ 2. RAG 检索        │
│ 3. 需求分析 Skill  │
│ 4. Reference       │
│ 5. LLM 生成        │
│ 6. 结果检查        │
└───────────────────┘
```

这样代码 AI 就不会把"Workflow"直接当成用户看到的产品功能。

## 四、Skill 到底怎么配置？

建议给代码 AI 明确一个 Skill 的数据结构：

```
Skill
├── 基础信息
│   ├── 名称
│   ├── 描述
│   ├── 所属业务线
│   └── 状态
│
├── 输入
│   ├── 输入参数
│   └── 参数说明
│
├── 能力规则
│   ├── 角色
│   ├── 执行规则
│   └── 约束条件
│
├── 输出
│   ├── 输出格式
│   └── 输出字段
│
└── Prompt 配置
```

**示例：**

| 属性 | 内容 |
|------|------|
| **Skill 名称** | 需求分析 Skill |
| **输入** | 用户需求 |
| **执行规则** | 1. 识别用户问题 2. 分析用户目标 3. 拆解业务需求 4. 识别异常场景 |
| **输出** | 需求分析结果 |

## 五、Reference 不要让代码 AI 理解成"另外一个知识库"

| 概念 | 回答的问题 | 示例 |
|------|-----------|------|
| **RAG 知识** | 企业现在到底是什么情况？ | 会员积分规则：普通会员 12 个月过期，VIP 会员永久有效 |
| **Reference** | 应该参考什么标准来完成？ | 公司 PRD 模板：1. 背景 2. 目标 3. 用户故事 4. 功能设计 5. 异常场景 6. 验收标准 |

**结论：**
- RAG = 事实知识
- Reference = 标准 / 案例 / 模板

两者可以同时使用。

## 六、RAG 流程也必须写清楚

代码 AI 最容易把 RAG 简单做成：上传 PDF → 向量化 → 搜索

实际设计应该是：

```
上传原始文档
      ↓
文档解析
      ↓
标准化处理
      ↓
AI / 人工分类
      ↓
打标签
      ↓
Chunk 切分
      ↓
Embedding 向量化
      ↓
向量库
      ↓
检索
      ↓
过滤
      ↓
召回
      ↓
返回给 Workflow
```

**Chunk 不是一个独立业务文档，它是从父文档切出来的知识片段。**

例如：

```
会员积分规则 V3.0
        │
        ├── Chunk 001：积分有效期
        ├── Chunk 002：积分获取规则
        ├── Chunk 003：积分兑换规则
        └── Chunk 004：积分失效规则
```

这个父子关系一定要告诉代码 AI。

## 七、Chunk 的元数据也需要定义

建议至少定义：

```
Chunk
├── chunk_id
├── document_id
├── content
├── sequence
├── business_line
├── knowledge_type
├── applicable_role
├── applicable_scene
├── version
├── permission
├── status
└── embedding
```

**注意：** 元数据不是用来"分类 Chunk 内容"这么简单，而是用于后续**检索过滤、权限控制和知识治理**。

例如：用户是测试人员，Workflow 要求：业务线=会员，角色=测试，状态=有效。那么 RAG 可以先通过元数据过滤，再做向量召回。

## 八、Prompt 组装也要明确

Prompt 需要分层设计：

```
最终 Prompt
= 全局 Prompt
+ 角色 Prompt
+ Workflow Prompt
+ Skill Prompt
+ Reference
+ RAG 结果
+ 用户输入
```

**示例：**

| 层 | 内容 |
|----|------|
| **全局** | 你是企业 AI 助手 |
| **角色** | 你是一名高级产品经理 |
| **Workflow** | 请完成需求分析 |
| **Skill** | 必须分析用户目标、业务流程、异常场景 |
| **Reference** | 按照公司 PRD 规范输出 |
| **RAG** | 会员积分业务规则 |
| **用户** | 帮我设计积分兑换优惠券 |

最终才交给 LLM。

## 九、意图识别不要做成固定下拉框

默认情况下用户通过自然语言输入，**不强制选择任务分类**。

**例如：**

> 用户："这个需求感觉有点问题，你帮我看看。"
>
> 系统通过 LLM 判断：
> - 可能意图：需求分析
> - 置信度：0.91
> - 调用：需求分析 Workflow

如果置信度很低：
> 你是希望：A. 分析需求 B. 生成 PRD C. 生成测试用例

才进行澄清。

这样 AI 工作台才不会退化成传统的"功能菜单"。

## 十一、状态机也要写清楚

否则代码 AI 很可能只做一个"保存"。

**Workflow 状态：**
```
草稿 → 测试中 → 待审核 → 已发布 → 已下线
```

**Skill 状态：**
```
草稿 → 测试中 → 已发布 → 停用
```

**知识状态：**
```
待处理 → 处理中 → 待审核 → 已发布 → 已失效
```

## 十二、AI 回答出现问题时，系统怎么定位？

每次 AI 请求应该产生一条执行记录：

```
请求 ID
 │
 ├── 用户输入
 ├── 意图识别结果
 ├── Workflow
 ├── RAG 检索
 │     ├── 查询词
 │     ├── 召回 Chunk
 │     └── 召回分数
 ├── Skill
 ├── Reference
 ├── Prompt 版本
 ├── Model
 └── 最终输出
```

当用户说"这次回答明显不对"时，管理员可以顺着链路排查：

```
是意图错了？ → 不是
Workflow 错？ → 不是
RAG 没找到知识？ → 是
最终定位：知识召回问题
```

而不是简单认为"大模型回答错了"。

## 十三、代码 AI 最容易脑补错的 10 个地方

作为开发约束，直接放到文档最后：

1. 用户默认通过自然语言使用 AI，不强制选择任务类型。
2. AI 能力不是 Workflow 本身，Workflow 是 AI 能力的执行流程。
3. RAG 属于知识获取能力，由 Workflow 根据场景决定是否调用。
4. 知识中心负责知识资产管理，不直接承担 AI 任务编排。
5. Skill 负责专业任务能力，不等于 Prompt。
6. Reference 负责模板、规范、案例等参考内容，不等于 RAG。
7. Tool 负责外部系统调用，Script 负责确定性程序执行。
8. Chunk 属于文档的子级知识片段，需要保留 document_id 父子关系。
9. Prompt 采用分层设计，不是一个固定 Prompt。
10. 每次 AI 执行都必须保留完整链路，支持问题定位和效果分析。
