# 知识中心需求说明书（Agent实施版）

> 用途：本文件直接提供给 AI Agent / Coding Agent，作为知识中心的产品需求与实现约束。  
> 目标：明确数据对象、页面、父子血缘、版本、状态、自动处理链路、元数据、上下线和异常处理，避免 Agent 自行脑补。

---

## 1. 产品目标

知识中心负责管理企业知识从原始文件进入系统，到最终形成可被 RAG 检索使用的向量数据的完整生命周期。

核心链路：

```text
原始文档
  ↓
标准化文档
  ↓
Chunk
  ↓
向量化数据
```

四个对象分别代表：

- **原始文档**：用户上传的原始文件，是知识源头。
- **标准化文档**：原始文档自动预处理后的规范化内容。
- **Chunk**：标准化文档按标题切分后的知识片段。
- **向量化数据**：Chunk 经过 Embedding 后生成的向量，用于后续 RAG 检索。

四个对象分别对应四个独立列表页面。

---

# 2. 核心数据关系

第一期固定为：

```text
原始文档 1 : 1 标准化文档
标准化文档 1 : N Chunk
Chunk 1 : 1 向量化数据
```

因此：

```text
原始文档版本 V1
   ↓
标准化文档 V1
   ↓
Chunk-001 / Chunk-002 / Chunk-003
   ↓
Vector-001 / Vector-002 / Vector-003
```

### Chunk → Vector 为什么采用 1:1

第一期一个 Chunk 使用一个 Embedding 模型生成一条向量记录。

暂不考虑：

- 一个 Chunk 对应多个 Embedding 模型；
- 多模型向量并存；
- 向量重新生成；
- 向量模型切换；
- 多版本向量并存。

---

# 3. 数据血缘与父级 ID

每一层数据必须保存父级 ID，并支持从列表点击父级 ID 跳转。

```text
文档ID
  ↓
版本ID
  ↓
标准化文档ID
  ↓
Chunk ID
  ↓
Vector ID
```

具体要求：

- 标准化文档列表必须展示原始文档 ID。
- Chunk 列表必须展示标准化文档 ID。
- 向量化数据列表必须展示 Chunk ID。
- 所有父级 ID 都可点击。
- 点击后进入对应父级详情。

因此任意 Vector 都必须能够追溯到：

```text
Vector
 ↓
Chunk
 ↓
标准化文档
 ↓
文档版本
 ↓
原始文档
```

这是知识中心的核心能力之一。

---

# 4. 文档与文档版本必须区分

“文档”是业务上的同一份知识；“版本”是该文档某一次具体内容。

例如：

```text
DOC-001：公司PRD规范
├── V1
├── V2
└── V3（当前生效）
```

每个版本都有自己完整的数据链：

```text
V1
├── 原始文档
├── 标准化文档
├── Chunk
└── Vector

V2
├── 原始文档
├── 标准化文档
├── Chunk
└── Vector
```

历史版本的数据必须保留，不得物理覆盖。

---

# 5. 原始文档列表

## 5.1 展示规则

原始文档页面是知识中心入口。

列表：

- 只展示当前最新版本对应的文档主记录；
- 按上传时间从近到远排序；
- 所有历史版本进入详情页管理。

### 版本号规则

如果文档尚未经过完整向量化处理：

```text
不展示版本号
```

不得因为上传就直接显示 V1。

只有完成正式知识处理、形成正式版本后，才形成：

```text
V1
```

后续：

```text
V1 → V2 → V3
```

列表始终只展示当前最新版本。

---

# 6. 原始文档上传

用户点击：

```text
上传文档
```

上传本地附件。

上传成功后：

```text
创建原始文档记录
审核状态 = 待审核
处理状态 = 未处理
生效状态 = 未生效
```

上传后立即执行第一阶段元数据 AI 识别。

---

# 7. 原始文档元数据

元数据分两个阶段生成。

## 7.1 第一阶段：原始文档上传后

AI 自动识别：

- 文件基础属性
- 文档类型
- 业务域
- 敏感等级
- 有效期

本阶段不采用人工配置标签体系。

## 7.2 人工修改

AI 识别后允许人工修改。

规则：

```text
AI识别
  ↓
人工修改
  ↓
人工修改值成为当前有效值
```

后续处理不得无理由覆盖人工修改结果。

---

# 8. 审核流程

上传后：

```text
待审核
```

审核中心审核。

结果：

```text
待审核
 ├── 审核通过
 └── 审核失败
```

## 审核通过

进入：

```text
审核通过
```

此时原始文档操作栏显示：

```text
生成向量数据
```

## 审核失败

进入：

```text
审核失败
```

操作栏显示：

```text
重新发起审核
```

点击后：

```text
审核失败 → 待审核
```

重新进入审核流程。

# 9. 原始文档操作

主要操作：

```text
预览
生成向量数据
删除
发布新版本
上线
下线
重新发起审核
```

按钮必须根据当前状态动态展示。

# 10. 预览

每条原始文档操作栏提供：

```text
预览
```

用于查看用户上传的原始文件。

预览不改变任何数据状态。

---

# 11. 生成向量数据

这是原始文档页面唯一触发知识处理链路的入口。

**页面不存在“标准化处理”按钮。**

用户只点击：

```text
生成向量数据
```

系统自动执行：

```text
原始文档
  ↓
标准化处理
  ↓
Chunk 切分
  ↓
Chunk 元数据 AI 识别
  ↓
向量化
```

用户不能单独触发上述中间步骤。

## 前置条件

只有：

```text
审核状态 = 审核通过
```

且当前版本尚未完成知识处理时，才能点击。

---

# 12. 自动标准化处理

原始文档进入标准化处理。

标准化预处理包括：

1. 文本清洗
2. 文档结构标准化
3. 表格处理
4. 图片/OCR处理
5. 基础文档信息整理

## 表格处理

表格必须跟随其所属标题纳入对应结构。

例如：

```text
## 订单权限

|角色|权限|
|---|---|
|产品经理|编辑|
|管理员|管理|
```

标准化结果仍需表达：

```text
## 订单权限

角色：产品经理
权限：编辑

角色：管理员
权限：管理
```

不得把表格无结构地打散成普通文本。

---

# 13. Chunk 切分

标准化文档完成后自动切 Chunk。

## 第一版切分规则

**只按标题切分。**

要求：

- 以标题层级作为主要切分依据；
- 一个 Chunk 对应一个完整标题章节；
- 不允许跨章节切分；
- 标题及其内容属于同一个 Chunk；
- 表格跟随所属标题进入该 Chunk。

示例：

```text
# CRM系统

## 订单管理
订单创建、修改、取消……

## 会员管理
会员注册、会员等级……
```

生成：

```text
Chunk-001
标题：订单管理
内容：订单创建、修改、取消……

Chunk-002
标题：会员管理
内容：会员注册、会员等级……
```

不得把“订单管理”和“会员管理”合并到同一个 Chunk。

---

# 14. Chunk 元数据

Chunk 阶段是第二阶段元数据处理。

## 14.1 继承原始文档元数据

Chunk 自动继承源头原始文档的元数据：

```text
原始文档：
文档类型 = 产品规范
业务域 = CRM
敏感等级 = 内部
有效期 = 2027-12-31

Chunk：
文档类型 = 产品规范
业务域 = CRM
敏感等级 = 内部
有效期 = 2027-12-31
```

## 14.2 Chunk 自身新增元数据

AI 根据 Chunk 的语义内容自动识别业务标签。

例如系统识别：

```text
Chunk：
用户购买商品后，可以在订单中心查看历史购买记录。
```

AI 判断：

```text
业务功能 = 订单
```

不是简单做字符串关键词匹配，而是：

> **使用 AI 进行语义判断。**

---

# 15. Chunk 标签允许多值

一个 Chunk 可以同时属于多个业务功能。

例如：

```text
业务功能：
订单
会员
```

因此标签字段必须支持多值。

---

# 16. 向量化

每个 Chunk 进行 Embedding。

第一期：

```text
1 Chunk : 1 Vector
```

例如：

```text
Chunk-001
  ↓
Vector-001
```

向量数据至少保存：

- Vector ID
- Chunk ID
- Embedding 模型
- 向量维度
- 向量化状态
- 创建时间
- 更新时间

列表不直接展示完整向量数组。

详情页可以展示技术信息。

---

# 17. 异步处理与进度

点击“生成向量数据”后，后台异步执行，不阻塞页面。

必须展示：

- 总体处理状态；
- 当前处理阶段；
- 处理进度；
- 失败阶段；
- 失败原因。

例如：

```text
处理状态：处理中

标准化处理     ✓
Chunk切分      ✓
元数据识别     进行中
向量化         -
```

失败示例：

```text
处理状态：处理失败
失败阶段：Chunk切分
失败原因：文档解析异常

[重新处理]
```

---

# 18. 失败重试

每个处理阶段有独立状态。

例如：

```text
标准化       成功
Chunk        成功
元数据识别    失败
向量化       未执行
```

点击重新处理后，从失败阶段继续。

即：

```text
元数据识别失败
  ↓
重新执行元数据识别
  ↓
向量化
```

已经成功且结果有效的上游阶段无需重复执行。

---

# 19. 批量生成向量数据

原始文档列表支持批量选择审核通过的文档。

点击：

```text
批量生成向量数据
```

后台创建异步处理任务。

每个文档独立处理。

例如：

```text
批次001

DOC001  成功
DOC002  处理中
DOC003  失败
```

一个文档失败不得影响其他文档。

---

# 20. 删除规则

关键规则：

> **是否允许删除，以是否已经完成向量化处理为判断依据，而不是是否已经完成标准化处理。**

## 20.1 向量化前

只要当前版本尚未完成向量化处理，就允许删除。

例如：

```text
待审核
审核失败
审核通过但未处理
处理中
处理失败
```

均可以删除。

## 20.2 向量化完成后

一旦该版本完成：

```text
标准化
↓
Chunk
↓
Chunk元数据
↓
向量化
```

并形成正式版本：

> 不允许删除。

之后只能使用：

```text
下线
```

控制有效性。

---

# 21. 新版本

已经形成正式版本的文档支持：

```text
发布新版本
```

例如当前：

```text
V1
```

发布后创建：

```text
V2
```

V2 必须重新走完整流程：

```text
审核
 ↓
标准化
 ↓
Chunk
 ↓
Chunk元数据
 ↓
向量化
```

不得直接复用 V1 的 Chunk 或 Vector 作为 V2 的最终知识数据。

---

# 22. 新版本生效规则

采用“旧版本继续生效”的策略。

例如：

```text
V1 = 当前生效

发布 V2
 ↓
V2 处理中

V1 = 继续生效
V2 = 处理中
```

如果 V2 失败：

```text
V1 = 继续生效
V2 = 失败
```

如果 V2 全部处理成功：

```text
V2 = 当前生效
V1 = 历史版本
```

新版本不会造成知识库空窗期。

---

# 23. 历史版本

历史版本必须全部保留。

例如：

```text
DOC001
├── V1
│   ├── 原始文档
│   ├── 标准化文档
│   ├── Chunk
│   └── Vector
├── V2
│   ├── 原始文档
│   ├── 标准化文档
│   ├── Chunk
│   └── Vector
└── V3
    ├── 原始文档
    ├── 标准化文档
    ├── Chunk
    └── Vector
```

原始文档详情页展示所有历史版本。

---

# 24. 回溯 AI 回答引用版本

未来 AI 回答必须能够知道自己引用了哪个具体版本。

例如：

```text
AI回答
 ↓
引用 Chunk-008
 ↓
Chunk-008 属于标准化文档 STD-003
 ↓
STD-003 属于 DOC001-V3
 ↓
DOC001 = 公司PRD规范
```

因此 RAG 检索记录至少需要保留：

```text
document_id
version_id
standardized_document_id
chunk_id
```

这样才能支持：

- 回答引用溯源；
- 问题定位；
- 版本审计；
- 知识质量分析。

---

# 25. 下线

支持单个和批量下线。

下线后：

```text
原始文档版本 = 下线
标准化文档 = 失效
Chunk = 失效
Vector = 失效
```

但是：

> **所有数据仍然保留，不物理删除。**

下线后的子数据不得参与 RAG 检索和引用。

---

# 26. 上线

下线文档支持：

```text
上线
```

支持批量上线。

上线后：

```text
原始文档版本 = 上线
标准化文档 = 有效
Chunk = 有效
Vector = 有效
```

重新允许参与 RAG 检索。

# 30. 状态模型

建议拆成三个维度，而不是把所有状态塞进一个字段。

## 审核状态

```text
待审核
审核通过
审核失败
```

## 处理状态

```text
未处理
处理中
处理成功
处理失败
```

## 生效状态

```text
未生效
已上线
已下线
```

这样可以表达：

```text
审核通过
+
处理中
+
当前V1继续上线
```

避免状态互相覆盖。

# 33. 完整流程

## 首次上传

```text
上传
 ↓
创建原始文档
 ↓
AI识别原始文档元数据
 ↓
待审核
 ↓
审核通过
 ↓
显示“生成向量数据”
 ↓
用户点击
 ↓
标准化
 ↓
按标题切Chunk
 ↓
AI识别Chunk元数据
 ↓
继承原始文档元数据
 ↓
Embedding
 ↓
生成Vector
 ↓
全部成功
 ↓
形成V1
 ↓
V1上线/生效
```

## 审核失败

```text
审核失败
 ↓
重新发起审核
 ↓
待审核
```

## 新版本

```text
V1当前生效
 ↓
发布新版本
 ↓
V2
 ↓
审核
 ↓
审核通过
 ↓
生成向量数据
 ↓
标准化
 ↓
Chunk
 ↓

 ↓

 ↓
全部成功
 ↓

```

```text

```

```text
 ↓

 ↓

```

# 34. Agent 硬性约束

以下内容不得由 Agent 自行改变：

1. 必须有四个独立列表：原始文档、标准化文档、Chunk、向量化数据。
2. 原始文档 → 标准化文档为 1:1。
3. 标准化文档 → Chunk 为 1:N。
4. Chunk → Vector 为 1:1。
5. 四层必须建立父级 ID。
6. 父级 ID必须可点击跳转。
7. 原始文档列表只展示当前最新文档记录。
8. 未形成正式版本时不得显示版本号。
9. 历史版本全部在原始文档详情页管理。
10. 原始文档页面只有“生成向量数据”入口，不提供独立的标准化/Chunk/标签/向量化按钮。
11. 生成向量数据后自动完成整个知识处理链路。
12. Chunk第一期只按标题切分。
13. Chunk不得跨章节。
14. 表格随所属标题进入对应Chunk。
15. Chunk元数据使用AI语义判断。
16. 一个Chunk允许多个标签值。
17. Chunk继承原始文档元数据。
18. 原始文档元数据和Chunk元数据分两个阶段识别。
19. 元数据均由AI识别，人工允许修改。
20. 已经完成向量化处理的版本不得删除。
21. 历史版本不得物理删除。
22. 新版本处理期间旧版本继续生效。
23. 新版本完整处理成功后才替换当前版本。
24. 下线只改变有效性，不删除数据。
25. 下线数据不得参与RAG。
26. 必须支持从Vector回溯到Chunk、版本、原始文档。
27. 第一阶段不支持多Embedding模型和重新向量化。
28. 一个文档处理失败不得阻塞其他批量文档。
29. 处理阶段必须有进度和失败原因。
30. 失败允许从失败阶段重新处理。

# 35. 第一阶段明确不做

- 不提供用户单独执行标准化处理。
- 不提供用户单独执行 Chunk 切分。
- 不提供用户单独执行 Chunk 标签处理。
- 不支持多 Embedding 模型。
- 不支持一个 Chunk 多个 Vector。
- 不支持重新向量化。
- 不支持多版本 Vector 并存。
- 不允许删除已经完成向量化的版本。
- 不物理删除历史版本。
- 不采用人工维护的 Chunk 标签值配置体系。
- 不采用简单关键词匹配进行 Chunk 分类。
- 不允许 Chunk 跨标题章节。
- 不允许不同版本混用 Chunk 或 Vector。

# 36. 产品设计原则

知识中心的本质不是普通文件管理，而是：

> **以原始文档为知识源头，以文档版本为隔离单位，自动完成标准化、Chunk、AI元数据识别和向量化，并通过父级 ID 建立完整数据血缘，最终为 RAG 提供可追溯、可版本管理、可上下线控制的知识数据。**

实现时优先保证三个能力：

### 1. 血缘追溯

```text
Vector
 ↓
Chunk
 ↓
StandardizedDocument
 ↓
Version
 ↓
Document
 ↓
原始文件
```

### 2. 版本隔离

```text
V1 → Chunk V1 → Vector V1

V2 → Chunk V2 → Vector V2
```

不得让 V2 使用 V1 的最终知识数据。

### 3. 有效性控制

RAG 正常检索只能使用：

```text
审核通过
+
处理完成
+
当前有效
+
已上线
```

的数据。

下线数据即使仍然保存在数据库，也不得参与正常检索。

# 37. 给 Agent 的实现边界

Agent 在实现页面、数据库、接口和处理流程时，应严格遵循本文档。

如果发现本文档未定义的细节：

1. 不得擅自改变已经明确的业务规则；
2. 可以采用最简单、可扩展的技术实现；
3. 对影响数据模型、状态机、版本机制、RAG有效性的事项，应先提出澄清问题；
4. 不要因为技术实现方便而取消版本、父级ID、状态或血缘关系；
5. 不要把四层对象合并成一个列表；
6. 不要把“生成向量数据”拆成需要用户逐步操作的多个按钮。
