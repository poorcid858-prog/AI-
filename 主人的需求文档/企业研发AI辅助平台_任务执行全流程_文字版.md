# 企业研发AI辅助平台——任务执行全流程（含 Workflow / Skill / RAG / Reference / Tool / Script）

> 本文档由《企业研发AI辅助平台—任务执行全流程》流程图完整转写而来。
>
> **示例场景：**产品经理输入：“我们准备增加一个会员积分兑换优惠券的功能，用户可以使用100积分兑换一张10元优惠券。帮我整理一份产品需求文档。”
>
> **目标：**完整描述一次AI任务从“用户输入”到“结果返回”的执行过程，以及 Workflow、Skill、RAG、Reference、Tool、Script、Prompt、LLM、质量检查等环节分别负责什么。

---

# 一、总体任务执行流程

```text
1. 意图识别
    ↓
2. Workflow编排
    ↓
3. 执行步骤（Skill / Tool / Script）
    ↓
4. 知识检索（RAG）
    ↓
5. Reference参考资料
    ↓
6. LLM生成
    ↓
7. 质量检查
    ↓
9. 返回结果
```

> 图中流程编号直接保留原图标注，原图从“7.质量检查”后直接标注“9.返回结果”。

# 二、步骤1：意图识别

## 2.1 作用

系统使用意图识别能力理解用户真实意图，判断：

- 用户想做什么
- 任务类型是什么
- 属于什么业务
- 用户扮演什么角色
- 关键业务信息是什么
- 对用户输入的理解置信度是多少

## 2.2 使用的要素

```text
意图识别模型（LLM）
意图识别Script
```

## 2.3 输入

用户原始输入：

> “我们准备增加一个会员积分兑换优惠券的功能，用户可以使用100积分兑换一张10元优惠券。帮我整理一份产品需求文档。”

## 2.4 输出

示例输出：

- 任务类型：PRD生成
- 业务线：会员
- 角色：产品经理
- 置信度：0.96
- 关键意图提取：
  - 积分兑换优惠券
  - 100积分 = 10元优惠券

## 2.5 流程中的作用

```text
用户自然语言
    ↓
理解用户意图
    ↓
判断任务类型 / 业务线 / 角色
    ↓
为后续Workflow选择提供依据
```

---

# 三、步骤2：Workflow编排

## 3.1 作用

根据意图识别结果，选择合适的Workflow（例如“PRD生成Workflow”），确定接下来具体执行哪些步骤以及步骤之间如何流转。

## 3.2 使用的要素

```text
Workflow引擎
PRD生成Workflow
```

## 3.3 输入

```text
意图识别结果
```

## 3.4 输出：执行计划

示例执行计划：

```text
Step1 需求分析
→
Step2 知识检索
→
Step3 获取Reference
→
Step4 生成PRD
→
Step5 质量检查
→
Step6 输出
```

## 3.5 Workflow的核心职责

Workflow负责：

- 定义任务执行流程
- 定义步骤顺序
- 定义条件分支
- 决定什么时候调用什么能力
- 控制整个任务如何执行

Workflow本身不负责具体专业任务内容，而是负责“怎么组织这些能力”。

# 五、Step1：需求分析

## 5.1 发生了什么

对用户需求进行结构化分析：

- 理解用户需求
- 提取业务规则
- 拆解功能点
- 识别可能的缺口

## 5.2 使用的要素

```text
Skill：需求分析Skill
Script：需求分析预处理模板
```

## 5.3 输入

用户原始输入：

```text
我们准备增加一个会员积分兑换优惠券的功能，
用户可以使用100积分兑换一张10元优惠券。
帮我整理一份产品需求文档。
```

## 5.4 输出

需求分析结果，例如：

```text
业务：会员积分兑换优惠券
规则：100积分 = 10元优惠券
用户：会员
产品目标：支持积分兑换优惠券
缺口：
- 积分是否允许部分兑换？
- 优惠券是否可以叠加？
- 有效期如何设置？
- 其他关键业务规则需要补充
```

# 六、Step2：知识检索（RAG）

## 6.1 发生了什么

在企业知识库中检索与当前任务相关的：

- 业务知识
- 规则
- 历史PRD
- FAQ等

## 6.2 使用的要素

```text
RAG检索引擎
（Embedding + 向量库 + 检索）
检索Script
```

图中明确说明：

> RAG检索引擎 = Embedding + 向量库 + 检索

检索Script用于：

> 构造查询 + 过滤规则

## 6.3 输入

```text
需求分析结果
```

## 6.4 检索过程

```text
需求分析结果
    ↓
构造查询
    ↓
Embedding
    ↓
向量库检索
    ↓
按照过滤规则进行筛选
    ↓
返回相关知识
```

## 6.5 示例检索关键词

```text
会员
积分
兑换优惠券
```

## 6.6 示例检索结果

TOP-K相关知识：

```text
1. 《会员积分兑换规则》片段
2. 《优惠券业务规则》片段
3. 《历史积分兑换PRD》片段
```

同时保留相关元数据，例如：

```text
来源
相似度
```

## 6.7 RAG在整个任务中的作用

RAG解决的是：

> 从企业知识库中找到与当前任务相关的知识。

RAG输出的是：

```text
相关知识片段
+
元数据
```

# 七、Step3：获取Reference

## 7.1 发生了什么

根据当前任务，把需要参考的规范、模板、案例等资料整合进后续生成过程。

## 7.2 使用的要素

```text
Reference管理
（规范/模板库/案例库）
Tool：Reference选择工具
（根据任务类型匹配）
```

## 7.3 输入

```text
任务类型
业务场景
检索结果
```

## 7.4 Reference示例

可能获取：

```text
公司PRD规范V3.2
PRD模板（标准版）
优秀案例：积分兑换PRD示例
```

## 7.5 输出

```text
Reference列表
```

## 7.6 Reference的作用

Reference用于提供：

- 规范
- 模板
- 案例
- 企业标准
- 优秀输出参考

这里的Reference不是企业事实知识本身，而是给模型提供“应该参考什么标准、模板和案例”。

# 八、Step4：生成PRD

## 8.1 发生了什么

调用PRD生成Skill，将：

- 用户需求
- 需求分析结果
- RAG知识
- Reference

组合起来，生成PRD初稿。

## 8.2 使用的要素

```text
Skill：PRD生成Skill
Script：PRD生成提示词模板
Tool：结构化输出工具
```

图中对Tool的说明为：

> 将生成结果按PRD结构组织。

## 8.3 输入

```text
需求分析结果
+
Reference集合
+
前面步骤产生的相关信息
```

## 8.4 输出

PRD初稿（结构化内容），例如包含：

```text
- 背景
- 目标
- 用户
- 业务流程
- 功能需求
- 业务规则
- 异常场景
- 数据要求
- 验收标准
```

# 九、Step5：质量检查

## 9.1 发生了什么

对生成的PRD进行再次检查，确认：

- 完整性
- 合规性
- 一致性
- 是否存在风险或缺失

## 9.2 使用的要素

```text
Skill：质量检查Skill
Script：质量检查规则脚本
Tool：规则校验工具
```

## 9.3 输入

```text
PRD初稿
+
Reference规范
```

## 9.4 检查项

图中给出的检查项包括：

```text
完整性：通过（90%）
合规性：通过
缺失项：优惠券是否可叠加？
风险提示：积分兑换情况未说明
```

## 9.5 是否通过？

存在一个判断节点：

```text
检查通过？
├── 是
│   ↓
│  根据检查报告，回到对应步骤
│  （如Step1补充分析 / Step4重新生成）
│
└── 否
    ↓
   继续处理
```

> 原图的判断逻辑通过“是/否”分支连接到后续流程，并强调如果检查发现问题，可以回到对应步骤进行补充分析或重新生成。

# 十、步骤4：Prompt组装

在执行完前面的业务步骤后，进入Prompt组装阶段。

## 10.1 发生了什么

将所有前置步骤产生的信息以及Prompt模板进行组合，构造最终发送给大模型的Prompt。

## 10.2 使用的要素

```text
Prompt组装引擎
Prompt模板
Script：Prompt拼装脚本
```

## 10.3 输入

```text
需求分析结果
+
Reference集合
+
PRD生成要求
```

## 10.4 组装逻辑

图中表达为：

> 将所有信息按照Prompt模板组织，构造完整上下文，准备调用大模型。

因此可以理解为：

```text
用户需求
+
需求分析结果
+
RAG检索结果
+
Reference
+
Skill规则
+
Prompt模板
+
输出要求
↓
完整Prompt
```

# 十一、步骤5：LLM生成

## 11.1 发生了什么

将完整Prompt发送给大模型，由大模型理解上下文并生成自然语言结果。

## 11.2 使用的要素

```text
大模型（LLM）
Tool：模型调用工具（API接入）
```

## 11.3 输入

```text
完整Prompt
```

## 11.4 输出

```text
PRD最终稿
```

示例：

```text
会员积分兑换优惠券PRD
├── 一、需求背景
├── 二、需求目标
├── 三、用户角色
├── 四、业务流程
├── 五、功能需求
├── 六、业务规则
├── 七、异常场景
└── 八、验收标准
```

# 十二、步骤6：质量检查（最终）

图中在LLM生成后再次设置了最终质量检查。

## 12.1 作用

对最终生成结果再次检查，确保：

- 内容符合要求
- 没有明显遗漏
- 符合Reference规范
- 满足输出要求

## 12.2 使用的要素

```text
Skill：最终质量检查Skill
Script：最终质量检查脚本
```

## 12.3 输入

```text
PRD最终稿
+
Reference规范
```

## 12.4 输出

最终检查报告：

```text
通过 / 不通过
```

图中给出的判断含义：

> 通过：认为结果可以返回用户。

> 不通过：需要根据检查结果重新处理。

# 十四、各要素在流程中的角色与作用

## 14.1 意图识别（LLM + Script）

**作用：**

理解用户真实意图，判断任务类型、业务线、角色等。

**输入：**

用户原始需求。

**输出：**

任务类型 / 业务线 / 角色 / 关键信息 / 置信度。

---

## 14.2 Workflow（编排引擎）

**作用：**

定义任务的执行流程、步骤顺序、条件分支和能力调用关系。

**特点：**

> 不生产内容，只负责流程控制。

**输入：**

意图识别结果。

**输出：**

执行计划。

---

## 14.3 Skill（能力）

**作用：**

完成某一类具体专业任务。

例如：

- 需求分析
- PRD生成
- 质量检查

**输入：**

步骤所需的输入。

**输出：**

结构化结果。

**特点：**

> 可复用、可组合。

---

## 14.4 RAG（知识检索）

**作用：**

从企业知识库中找到与任务相关的知识。

**来源：**

企业知识库。

**输入：**

查询。

**输出：**

相关知识片段及元数据。

---

## 14.5 Reference（参考资料）

**作用：**

为模型提供规范、模板、案例等参考资料。

**来源：**

- 规范库
- 模板库
- 案例库
- RAG检索结果等

**输出：**

Reference集合。

---

## 14.6 Tool（工具）

**作用：**

完成系统无法直接通过模型生成的外部能力调用。

图中举例：

- Reference选择工具
- 模型调用工具
- 结构化输出工具
- 导出工具

**特点：**

> 确定、可控、可调用。

---

## 14.7 Script（脚本/提示词模板）

**作用：**

定义一些固定的处理逻辑、规则或提示词模板。

图中示例：

- 意图识别Script
- 需求分析预处理模板
- 检索Script
- PRD生成提示词模板
- 质量检查规则脚本
- Prompt拼装脚本
- 最终质量检查脚本

**特点：**

> 可配置、可版本管理。

---

## 14.8 LLM（大模型）

**作用：**

理解上下文并生成自然语言内容。

**输入：**

完整Prompt。

**输出：**

生成结果。

# 十八、流程中的核心关系

```text
用户
 ↓
意图识别
 ↓
Workflow
 ↓
Workflow决定：
 ├── 调用哪个Skill
 ├── 什么时候调用RAG
 ├── 什么时候获取Reference
 ├── 什么时候调用Tool
 ├── 什么时候执行Script
```

因此：

```text

Prompt = 组织模型输入
```

# 二十、给代码AI的核心理解

> 一次AI任务不是简单的“用户问题 → LLM → 答案”，而是由意图识别、Workflow编排、多个Skill/Tool/Script步骤、RAG知识检索、Reference参考资料、Prompt组装、LLM生成和质量检查共同组成。Workflow负责控制整个执行过程；Skill负责具体专业任务；RAG负责从企业知识库检索事实知识；Reference负责提供规范、模板和案例；Tool负责确定性的外部能力调用；Script负责固定规则和模板逻辑；Prompt负责把前置结果组织成模型可理解的上下文；LLM负责最终理解和生成。整个执行链路需要保留输入、各步骤结果和最终输出，以便后续质量分析和问题定位。
