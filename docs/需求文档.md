## 一、产品定位

**一句话**：把企业散落在 Word/PDF/PPT 里的知识，加工成 AI 能准确引用的知识库，
让产品、测试、前端三类研发角色能在几分钟内产出有企业上下文的基础文档。

**和"直接用 ChatGPT"的区别**（这是整个项目存在的理由）：

| | 直接问通用 AI | 本平台 |
| --- | --- | --- |
| 知识来源 | 公开互联网 | 企业内部已审核文档 |
| 越权风险 | 无企业数据，但也没用 | 业务线 × 密级双重隔离 |
| 编造 | 不知道就编 | 检索不到就明确说没有，不编 |
| 可追溯 | 无出处 | 每条结论标注来自哪份文档哪一章 |
| 越用越好 | 不会 | 优秀问答回流案例库 |

**核心设计原则**（贯穿全文，也是本项目的技术底线）：

1. **前端隐藏是体验，后端拦截才是安全** —— 页面上不显示的东西，接口也必须拦。
2. **调用方过滤是优化，引擎过滤才是安全** —— 权限判断必须写在检索引擎内部，
   不能依赖"调用的人记得先过滤"。
3. **宁可答不出，不可答错** —— 检索不到就承认不知道。企业场景里，
   错答的伤害远大于不答：不答你会去问人，错答你会直接用。

## 二、角色与权限

### 2.1 角色定义

| 角色 | 是谁 | 干什么 |
| --- | --- | --- |
| 产研用户 | 产品经理 / 测试 / 前端工程师 | 用 AI 助手生成 PRD、测试用例、前端组件 |
| 客服 | 对外客服（含 AI 客服） | 回答客户问题，**只能接触公开级内容** |
| 知识管理员 | 知识运营岗 | 上传、加工、维护知识库 |
| 审核人员 | 业务负责人 | 把关知识能不能进库、优秀问答能不能沉淀 |
| 技术管理员 | AI 平台工程师 | 管模型、向量库、检索调试 |
| 演示访客 | 外部访客（云端演示用） | 只读浏览，可切换体验身份 |

**职责分离原则**：**不能自己传自己审**。知识管理员能上传但不能审核，
审核人员能审核但不能上传。这是审计合规的基本要求。

### 2.2 权限维度一：业务线 × 密级（**这是本项目最核心的机制**）

密级四档，逐级包含：

| 密级 | 含义 | 举例 |
| --- | --- | --- |
| 公开 | 可对外 | 退款政策客户版、常见问题 |
| 内部 | 全员可见 | 产品需求规范、测试流程 |
| 机密 | 本业务线可见 | 定价策略、风控规则 |
| 绝密 | 管理层 | 成本结构、风控阈值 |

业务线：交易线 / 会员线 / 全线（`全线` 的内容对所有业务线可见）。

各角色的可见范围：

| 角色 | 业务线范围 | 密级上限 |
| --- | --- | --- |
| 产研用户 | 本人所属业务线 + 全线 | 机密 |
| 客服 | 本人所属业务线 + 全线 | **公开** |
| 知识管理员 | 全部 | 绝密 |
| 审核人员 | 全部 | 绝密 |
| 技术管理员 | 全部 | 绝密，但**涉密正文脱敏** |
| 演示访客 | 全部 | **公开**（可切换身份体验对比） |

> **技术管理员为什么要脱敏**：他为了调试需要看到管道里的东西（切分结果、
> 向量、检索打分），但不该看到绝密文档的正文。一句话原则——
> **技术管理员管管道，不管内容**。

### 2.3 权限维度二：对文档四层的操作权限

| 知识对象 | 产研用户 | 客服 | 知识管理员 | 审核人员 | 技术管理员 |
| --- | --- | --- | --- | --- | --- |
| 原始文档 | 查看有权限的（机密及以上仅在线预览，不可下载） | 仅公开级 | 查看/上传/删除/重新加工 | 查看/审核 | 只看状态与结构，正文脱敏 |
| 标准化文档 | 不直接看 | 不看 | 查看/修改/重新处理 | 查看/审核 | 同上，脱敏 |
| Chunk | 不直接看，但 AI 回答会引用并标注出处 | 同左 | 查看/修改/重新切分 | 只看质量异常的片段 | 查看/调试，正文脱敏 |
| 向量数据 | 不可见 | 不可见 | 只看处理状态 | 不可见 | 管理/调试 |

> 为什么产研用户"不直接看"标准化文档和 Chunk：这两层是加工中间产物，
> 给业务用户看只会造成困扰（"为什么这段话被切成两半"）。
> 他们需要的是 AI 回答 + 可点击的出处链接。

## 三、知识加工流程（14 步）

### 3.1 完整流程

```
①  文件上传        登记元数据：文件名、类型、上传人、上传时间、
                   业务线、版本、密级、负责人、状态
②  文件解析        Word/PDF/PPT → 文本
                   · 表格转 Markdown，保留行列关系
                   · 图片记录位置 + 图注
                   · 解析失败 → 进「解析失败」状态，附原因 + 重试入口
③  内容清洗        去页眉页脚、修订痕迹、乱码、多余空白
④  内容结构化      章节层级归整为统一格式（一级标题/二级标题/正文/表格）
⑤  打标签          业务线、知识类型、适用角色、版本、有效时间、密级、负责人
⑥  质量检查（一）  文档级：结构是否完整、表格是否洗坏、密级是否缺失
                   → 不合格退回知识管理员
★⑦ 人工审核        审核员看「原文 ↔ 加工结果」并排对照，决定能否进库
                   通过 → 继续；驳回 → 归档并记录原因
⑧  文档切分        按章节切 Chunk，保留章节路径
⑨  内容去重        片段级跨文档指纹去重
⑩  质量检查（二）  片段级：过短/过长/纯标题/乱码 打分
                   异常片段单独挑出给审核员看
⑪  Embedding       每个 Chunk 向量化
⑫  写入向量库+索引 每条记录带「是否已发布」标记，未发布不参与检索
⑬  发布            翻牌为可检索，知识正式生效
⑭  下架/替换/归档  新版本发布时旧版自动归档；有效期到自动提醒复审
```

### 3.2 相比 v1 的四处修正及原因

**① 质量检查从第 11 步前移，并拆成两次**

v1 顺序是「写入向量库 → 建索引 → 质量检查 → 发布」。问题：**第 9 步一写进去，
AI 就能搜到了**。等第 11 步发现文档不合格，它已经污染了两步的检索结果。

改为：文档级检查在加工后（⑥），片段级检查在切分后（⑩），都在写入之前。
同时向量库每条记录带「是否已发布」标记，只有发布才翻牌。

> 这不是理论风险。本项目第 7 步真实发生过：建索引时漏带了「状态」字段，
> 导致未审核文档任何人都能检索到——因为权限过滤代码对"缺失状态"的处理是
> "按兼容旧数据放行"。两个各自合理的决定凑在一起，整层过滤就静默失效了。

**② 去重从第 4 步后移到切分之后**

切分之前只能按段落去重，但真正污染检索的是重复的**片段**：同一段话在 5 份
文档里都有，搜出来 5 条一模一样的，把本该出现的其他答案挤掉了。

**③ 新增第 14 步「下架/替换/归档」**

v1 只有上线没有下线。这是企业 RAG 最常见的翻车点：

> 产品经理让 AI 写 PRD，AI 引用了 2023 年已废弃的退款规则，
> 因为那份旧文档从来没人下架。

规则：
- 新版本发布时，旧版本自动转「已归档」——可查原文，不进检索
- 到「有效时间」自动提醒负责人复审
- 逾期未复审 → 降级为「待复审」，仍可检索，但 AI 答案里标注「此规则可能已过期」

**④ 明确人工审核关卡的位置和视图（第 7 步）**

一道关卡，不是三道。审核员看到的是「原文 ↔ 加工结果」并排对照：
既满足"上传后审核才生效"的业务要求，又能发现"清洗把关键表格洗坏了"这类问题。

Chunk 层不设人工关卡（一份文档能切出上百个片段，审不完），
改为自动打分 + 只把异常片段挑给审核员。

### 3.3 文档状态机

```
待解析 ──→ 解析失败 ──(重试)──┐
   │                          │
   ↓ ←───────────────────────┘
加工中 ──→ 质检不合格 ──(修正后重新加工)──┐
   │                                      │
   ↓ ←───────────────────────────────────┘
待审核 ──→ 已驳回（归档，记录原因）
   │
   ↓ 通过
待发布 ──→ 已发布 ──→ 待复审（有效期到）
              │
              ↓ 新版本上线 / 手动下架
           已归档（可查原文，不进检索）
```

## 四、四层文档模型

### 4.1 分层与职责

| 层 | 是什么 | 为什么要单独存 |
| --- | --- | --- |
| 第一层 原始文档 | 上传的 Word/PDF/PPT 原件 | **必须保留**：要支持查看原文、下载、重新解析、重新切分、更换 Embedding 模型、重建向量库 |
| 第二层 标准化文档 | 解析 → 清洗 → 去噪 → 格式归整 → 结构化后的版本 | 这是 **AI 实际读到的内容**，也是人工审核的对象 |
| 第三层 Chunk | 标准化文档切出的知识片段 | 检索的基本单位，也是 AI 引用时标注出处的粒度 |
| 第四层 Vector | 每个 Chunk 的向量表示 | 语义检索的计算基础 |

### 4.2 对应关系（v1 的 1:1 需要收紧）

```
原始文档 ──1:N──→ 标准化文档 ──1:N──→ Chunk ──1:N──→ Vector
              (每次重新加工                          (每个 Embedding
               产生新版本，                            模型一份)
               只有一个"当前生效")
```

v1 写的是「1 原始 → 1 标准化」。但你自己也提到"可能要重新解析、重新切分、
更换 Embedding 模型"——**每次重新加工都该产生新版本，只保留一个"当前生效"**。

理由：
- 1:1 等于覆盖，出了问题回不去
- 只有留着历史版本，才能回答"换了 Embedding 模型之后，检索效果是变好还是变差"
  ——这正是技术管理员做模型评估的基础

Chunk → Vector 同理是 1:N：一个片段在不同模型下各有一份向量。

### 4.3 字段设计

**共同字段**（四层都有，用于溯源）

| 字段 | 说明 |
| --- | --- |
| ID | 本层唯一标识 |
| 上层 ID | 指向上一层的记录（第一层为空）——溯源靠这个字段 |
| 文档名称 | 冗余存储，方便展示不用逐层回查 |
| 业务线 / 密级 | **权限判据，必须每层都带**（少带一层，那层过滤就失效） |
| 知识类型 | 需求文档 / 接口文档 / 测试规范 / 业务规则 / FAQ |
| 版本 | 语义版本号 |
| 状态 | 见 3.3 状态机 |
| 创建人 / 创建时间 / 更新时间 | 审计信息 |

**各层特有字段**

| 层 | 特有字段 |
| --- | --- |
| 原始文档 | 文件类型、文件大小、存储路径、上传人、负责人、标签、有效时间 |
| 标准化文档 | 章节结构树、加工日志（每一步做了什么）、质检得分、审核人、审核意见 |
| Chunk | 章节路径、序号、字数、内容指纹（去重用）、质量得分、Embedding 状态 |
| Vector | 向量模型名、向量维度、向量值、索引名 |

> **溯源要求**：从 AI 的任意一句回答，能一路点回：
> Vector → Chunk → 标准化文档的哪一章 → 原始文档的第几页。
> 这是企业场景敢用 AI 的前提。

### 4.4 溯源的交互设计

数据层面有「上层 ID」字段还不够，产品层面必须好用：

- **知识库页四层 Tab 切换**：原始文档 / 标准化文档 / Chunk / 向量，
  每一层都是独立列表，可筛选、可搜索
- **任意一条记录都有两个动作**：
  - 「向上追溯」→ 跳到它的上层记录
  - 「向下展开」→ 列出由它产生的下层记录（含数量，如"展开 37 个片段"）
- **完整面包屑**，任意层级都能看到自己在链条上的位置：

  ```
  订单管理规范.docx  >  标准化 v2  >  第3章 退款流程  >  Chunk 017  >  Vector(模型v1)
  ```

- **从片段一键「查看原文位置」**：显示它对应原始文档的第几章/第几页 + 该处原文内容

> **实现边界（如实说明）**：Word/PDF 里做像素级精确高亮成本很高，
> 本期做到「定位到第几章/第几页 + 展示对应原文片段内容」，不做原文高亮渲染。
> 对溯源的实际可用性影响很小。

## 五、平台功能结构

### 5.1 本期建设范围：4 深 2 浅

全部铺开的结果是每个功能都很浅，点开哪个都是空壳。本期取舍：

```
【深做】功能完整、有真实数据、可操作
├── AI 工作台
│   ├── 产品助手      需求 → PRD
│   ├── 测试助手      需求 → 测试用例
│   ├── 前端助手      需求 → 前端组件
│   ├── AI 对话       自由问答（带权限过滤）
│   ├── AI 客服对话   独立窗口，关键字匹配模式（见第七章）
│   └── 历史记录      可回溯、可反馈、可查召回详情
├── 知识中心
│   ├── 知识库        四层视图 + 逐层溯源（见 4.4）
│   ├── 文档管理      上传、加工、版本、重新加工、下架、删除
│   │                 —— 含影响预览（见第八章）
│   ├── 客服话术库    问答对 + 同义词表 + 未命中问题池（见第七章）
│   └── 知识质量      质检得分、异常片段
├── 审核中心
│   ├── 知识审核      原文 ↔ 加工结果 并排对照
│   ├── 优秀案例审核  问答对沉淀（见第六章）
│   └── 审核记录      审计流水
└── AI 能力中心      ★ v3 从「浅做」升级为「深做」
    ├── Skill        角色设定 / 任务指令 / 输出格式 / 边界约束 / 示例选取规则
    ├── Prompt       模板可编辑 + 版本 + 试跑对比 + 一键回滚
    ├── Reference    挂载参考资料（行业模板、规范文档）
    ├── Script/Tool  输出后处理（格式校验、字段补全）
    └── Workflow     步骤编排、每步用哪个 Skill、失败降级策略

【浅做】
├── AI 运营          ★ v3 从「浅做」进一步收窄以补偿能力中心的工作量
│   ├── RAG 检索分析  深做（第八章依赖它，是核心能力）
│   ├── 使用数据      深做
│   └── 效果数据 / 用户反馈 / 成本分析   简化图表
└── 系统管理         仅配置页骨架
    用户/角色/权限、模型配置、Embedding 配置、
    向量库配置、RAG 调试、AI 日志、系统配置
```

选这四个深做的理由：**它们连起来是一个完整闭环，且每一环都能独立讲出设计取舍**——
知识管理员传知识 → 审核员把关 → 产研用 AI 生成文档 →
管理员看召回详情发现问题 → 改文档或调参数 → 对比验证效果 → 反馈回流。

### 5.2 AI 能力中心「可编辑」的安全机制

Skill 和 Prompt 是「生成质量好不好」的直接原因，做成只读展示说服力不足，
所以 v3 升级为可真实配置。但**可编辑必须配一套护栏，否则等于给用户一把能砸自己的锤子**：

```
修改 → 存为草稿（不生效）
         ↓
      试跑：拿真实需求跑一遍
         ↓
      新旧版本输出并排对比
         ↓
      满意 → 发布生效        不满意 → 弃稿
         ↓
      保留最近 N 个版本，一键回滚
         ↓
      全程留痕：谁改的、改了什么、何时生效
```

> **一个架构一致性观察**：这套「草稿 → 对比 → 发布 → 可回滚」，
> 和第八章的「重新加工先出草稿再对比生效」、
> 第十章的「回答对比调试」是**同一个模式**。实现一次，三处复用。
> 这种一致性本身就是可讲的设计考量。

### 5.3 结构调整

**「知识审核」在 v1 里出现了两次**（知识中心和审核中心下面都有）。
调整为：审核入口只在审核中心，知识中心只显示审核状态。

## 六、双向反馈机制

系统越用越好的两条回路：

**回路一：优秀问答 → 提示词案例库**

用户对某次生成打了好评 → 进审核中心「优秀案例审核」→ 通过后进案例库
→ 下次遇到语义相近的需求，自动作为 Few-shot 示例注入提示词。

**回路二：AI 生成的有效内容 → 知识库**

AI 生成的内容如果不在知识库里但确实符合需求 → 审核通过后向量化入库。

### ⚠️ 这是全系统唯一可能"越用越差"的地方

AI 生成的内容一旦被审核员顺手点通过，就变成了"知识"，之后会被反复引用。
要是当初那条是 AI 编的，**这个错误就永久固化，而且越用越像真的**。

四条防护：

1. **来源必须标记**为「AI 生成 + 人工确认」，和「企业原始文档」在库里区分开
2. **检索排序权重低于原始文档**——同等相关度下，原始文档优先
3. **AI 引用它作答时，答案里必须标注**"此依据来自历史问答，非企业正式文档"
4. **审这类内容的必须是业务负责人**，不能是普通审核员——
   因为要判断内容对不对，不只是格式对不对

## 七、AI 客服（关键字匹配模式）

### 7.1 定位

**对外 AI 客服是内部平台的一个分支**：共用同一套账号体系和知识加工能力，
但有独立的知识库、独立的对话入口、**独立的检索模式**。

| | 内部 AI 助手 | 对外 AI 客服 |
| --- | --- | --- |
| 面向 | 企业员工 | 企业客户 |
| 检索模式 | **向量语义检索** | **关键字匹配** |
| 知识范围 | 全部（按角色过滤） | 客服话术库 + 企业知识库公开级 |
| 答不出时 | 说明检索不到 | **转人工**，并带上客户原话 |

### 7.2 为什么客服不用向量检索（本项目最好的技术对比素材）

这不是"偷懒"，是按场景选方案。四条理由：

1. **问题高度收敛**：客服问题 80% 是那几十个问题的变体，关键字够用且**结果可预测**
2. **可解释、可运营**：命中了哪个词运营看得懂、能自己维护同义词表；
   向量检索"为什么这条没召回"运营根本查不了
3. **错答成本极高**：对客户说错话是投诉甚至赔付。
   宁可答不出转人工，也不要"语义上接近但实际不对"
4. **可硬绑定**：法务要求"客户提到这个词必须回这个话术"，向量检索做不到强制

> **同一个平台里两种检索模式并存**，说明设计者不是"学了 RAG 就到处用"，
> 而是按场景权衡。这比多做三个页面有价值。

### 7.3 检索流程

```
客户提问："我买的东西不想要了，钱啥时候能回来"
        ↓
① 分词         不想要 / 了 / 钱 / 啥时候 / 回来
        ↓
② 停用词过滤   不想要 / 钱 / 啥时候 / 回来
        ↓
③ 同义词归一   ★ 关键一步（见 7.4）
               不想要 → 退货    钱+回来 → 退款
               啥时候 → 时效
        ↓
④ 关键字命中   在话术库中匹配：退货 / 退款 / 时效
        ↓
⑤ 打分排序     按命中词的权重和排序
               词权重 = 逆文档频率（罕见词权重高）
               例："退款"常见权重低，"跨境"罕见权重高
        ↓
⑥ 结果分流
   命中话术库        → 直接返回标准话术（已经过法务/运营审核）
   仅命中公开级文档  → 基于文档内容作答，标注出处
   零命中            → 转人工 + 记入「未命中问题池」
```

**结果优先级的意义**：**对客户说的话必须是审过的**。
话术库优先，公开级文档只做兜底。

### 7.4 同义词表 —— 这个方案的成败关键

纯关键字匹配最大的死穴是**口语和同义词**。客户不说"退款"，
他说"退钱"、"钱啥时候到"、"不想要了"、"能不能取消"。
没有同义词表，关键字匹配会大面积零命中。

| 要求 | 说明 |
| --- | --- |
| 运营可维护 | 知识管理员在页面上直接增删改，不需要发版 |
| 一词多形 | 一个标准词对应 N 个客户说法 |
| 可追溯效果 | 加了同义词之后命中率变化多少，看得见（见第十章） |

示例：

| 标准词 | 客户说法 |
| --- | --- |
| 退款 | 退钱、钱啥时候到、钱回来、返款、退回来 |
| 退货 | 不想要了、能不能退、寄回去、退掉 |
| 时效 | 多久、几天、什么时候、要等多长时间 |

### 7.5 未命中问题池

关键字模式零命中的概率比向量检索高得多，所以**必须有收集机制**。

- 客户问了但系统答不出的问题，全部记入未命中问题池
- 知识管理员看这个池子，判断是「缺同义词」还是「缺话术」
- 缺同义词 → 加进同义词表；缺话术 → 补充话术库条目

> **这是客服知识库唯一的成长路径。** 也是面试时很好讲的一环：
> 系统不是一次做好的，是靠"答不出的问题"驱动迭代的。

### 7.6 客服效果的硬指标

关键字模式相比向量检索的另一个好处：**效果可量化**。

| 指标 | 含义 |
| --- | --- |
| 话术库命中率 | 多少比例的客户问题命中了标准话术 |
| 公开级兜底率 | 多少比例靠公开文档作答 |
| 转人工率 | 多少比例答不出 |
| 平均命中关键字数 | 命中越多说明问题理解越准 |

改完同义词表重跑测试集，"命中率从 62% 涨到 87%、转人工从 38% 降到 13%"——
这个数字比任何描述都直观。

## 八、召回可观测与反向修复

> **这是本期最核心的运维能力。** 大多数 RAG 项目做到「能答」就停了，
> 做不到「答错了能查、能修、能验证修好了」。这一章是分水岭。

### 8.1 看得见：检索快照

每一次 AI 回答，都留一条完整的检索快照：

```
原始问题
   ↓
拆解结果            分词 / 停用词过滤 / （客服）同义词归一后的关键字
   ↓
权限过滤前的候选    共 N 条
   ↓
权限过滤            剔除了哪些、因为什么（业务线 / 密级 / 状态）
   ↓
召回结果            每条带：相似度分数、来自哪份文档哪一章、
                    Chunk ID、入选或淘汰的原因
   ↓
重排后的最终选择    实际塞进提示词的是哪几条
   ↓
提示词全文          Skill + 角色设定 + 知识 + Few-shot 示例
   ↓
AI 输出 + 质量校验结果
```

**两个入口**：

- **单条**：历史记录里每条回答旁边一个「查看召回」
- **整体**：AI 运营 → RAG 检索分析（召回率分布、常见零召回问题、
  高频引用片段排行）

### 8.2 改得动：三种修复动作

管理员看完召回详情发现问题后，三条修复路径：

| 动作 | 影响链路 | 用在什么场景 |
| --- | --- | --- |
| **改原始文档** | 重新加工 → 新版标准化文档 → 重新切分 → 重新向量化，旧版归档 | 内容本身就错了 |
| **调参数重新标准化** | 不动原文，重新生成标准化文档 + 片段 + 向量 | 内容对，但被切碎了 / 表格洗坏了 / 章节没识别对 |
| **删除文档** | 片段与向量连带失效 | 文档整体作废 |

**可调的标准化参数**（要具体，否则"可配置"是空话）：

| 参数 | 影响 |
| --- | --- |
| 切分粒度 | 按章节 / 按段落 / 固定字数（含重叠字数） |
| 片段最小长度 | 太小的片段信息量不足，检索命中了也没用 |
| 片段最大长度 | 太大会稀释语义，也占提示词额度 |
| 是否保留表格结构 | 保留则转 Markdown，否则拉平成文本 |
| **是否把章节标题拼进片段正文** | **对命中率影响最大的一个参数** |
| 清洗强度 | 去页眉页脚 / 去修订痕迹 / 合并短段落 |
| 去重阈值 | 多相似算重复 |

### 8.3 两个必须做的安全设计

**① 执行前必须显示影响预览**

```
⚠ 此操作将影响：
   · 1 份标准化文档（v2 → 归档）
   · 37 个知识片段
   · 37 条向量
   · 其中 12 个片段在过去 7 天被 AI 引用过 45 次

   [ 取消 ]  [ 确认执行 ]
```

不做这个，管理员调一个参数就可能把整条业务线的检索质量搞坏，而且毫不知情。

**② 重新加工不能直接覆盖，必须先出草稿版本**

```
调整参数 → 生成草稿版标准化文档（不生效）
              ↓
        新旧两版切分结果并排对比
        "这份文档从 37 个片段变成 22 个片段"
              ↓
        ★ 回归验证：拿历史真实问题重放一遍
          看召回是变好还是变坏
              ↓
        确认 → 发布生效        不满意 → 弃稿
```

> 这正是四层模型里「1:N 版本」设计真正发挥作用的地方——
> 当初坚持留版本，是为了这一刻。

**回归验证是这个功能最专业的部分**：不靠"我觉得变好了"，
而是拿真实历史问题跑数据。详见第十章的「回答对比调试」。

## 九、系统架构

```
                      知识管理员
                          │
                  上传企业原始知识
                          │
                 ┌────────▼────────┐
                 │   原始文档层     │  Word / PDF / PPT
                 └────────┬────────┘
                          │
                    知识加工 Pipeline
                          │
        ┌────────┬────────┼────────┬────────┐
        ↓        ↓        ↓        ↓        ↓
      解析     清洗    结构化    标签    质检(一)
        └────────┴────────┼────────┴────────┘
                          ↓
                  ★ 人工审核关卡
                    (原文 ↔ 加工结果 对照)
                          ↓
                   标准化知识文档层
                          │
                    切分 → 去重 → 质检(二)
                          ↓
                     Chunk 知识层
                          │
                     Embedding
                          ↓
                   Vector / Index 层
                          │
                     RAG 检索系统
                          ↓
              ★★ 权限过滤（业务线 × 密级 × 状态）
                          ↓
                    提示词组装（Skill / Prompt /
                    Reference / Few-shot 案例）
                          ↓
                         LLM
                          ↓
                     输出质量校验
                          ↓
                    ┌─────┴─────┐
                    ↓           ↓
                 用户使用    ✔ 用户好评
                                │
                        ┌───────┴───────┐
                        ↓               ↓
                   提示词案例库      知识库回流
                    (回路一)         (回路二)
                        └───────┬───────┘
                                ↓
                          回到 AI 能力中心 / 知识中心
```

相比 v1 架构图补了三处：

- **权限过滤**（★★）：v1 是「RAG 检索 → LLM」，实际必须是
  「RAG 检索 → 权限过滤 → LLM」。这是本项目最核心的机制，不该藏在实现细节里。
- **反馈回路**：v1 的图是单向的，看不到双向反馈。
- **AI 客服分支**（见下）：从 Chunk 知识层分叉出去的另一条检索链路。

### 9.1 AI 客服分支（关键字链路）

客服不走向量，从 Chunk 层直接分叉出一条独立链路：

```
                     Chunk 知识层
                          │
              ┌───────────┴───────────┐
              ↓                       ↓
        Embedding/Vector        客服话术库
        （内部研发用）           （问答对 + 同义词表）
              ↓                       ↓
        向量语义检索              关键字匹配检索
              ↓                       ↓
        权限过滤                  仅公开级
        (业务线×密级×状态)             ↓
              ↓                  ┌────┴────┐
        内部 AI 助手              ↓         ↓
        (产品/测试/前端)      命中话术   零命中
                                  ↓         ↓
                            返回标准话术  转人工
                                            ↓
                                     未命中问题池
                                            ↓
                                   知识管理员补同义词/话术
                                            │
                                            └──→ 回到话术库
```

**两条链路共享的**：知识加工 Pipeline、四层文档模型、审核机制。
**两条链路不共享的**：检索方式、知识范围、答不出时的兜底策略。

## 十、部署与访问方式

### 10.1 访问流程

访客不需要注册、不需要记账号，**一个链接 + 一次输密码**：

```
收到链接 → 打开 → 输入访问口令 → 落地页（无登录页）
                                      ↓
                              页面上快速切换角色
                              体验不同权限下的业务功能
```

### 10.2 一道门，两把钥匙 ★

**同一个链接、同一个输密码页，但有两个口令**：

| | 访客口令（发给别人） | 调试口令（仅 PM 持有） |
| --- | --- | --- |
| 进入后 | 演示模式 | **真实模式** |
| 浏览 / 生成 / 问答 | 完全真实 | 完全真实 |
| 快速切换角色 | 可以 | 可以 |
| 上传 / 删除 / 审核 / 改配置 | 能点、有影响预览、**不落库** | **真实生效** |
| 顶部标识 | 无 | 橙色横幅「真实模式 · 改动会保存」 |
| 恢复初始数据 | 不需要 | 有「一键恢复」按钮 |

**为什么必须分两个口令**：PM 需要真实删改文档来调试回答差异
（这是刚需——自己不能真实测，就不知道系统好不好用）。
但如果只有一个口令，就等于把删库权限发给了每一个拿到链接的人。

**三个隐患的处理**：

| 隐患 | 处理 |
| --- | --- |
| 访客把演示环境搞坏 | 演示模式写操作不落库 |
| PM 调试到一半正好有人来看 | 真实模式提供「一键恢复初始数据」，时机自己控制 |
| PM 误以为在演示模式而随手删了东西 | 真实模式常驻橙色横幅 + 危险操作过影响预览 |

**安全边界（必须写明）**：单一共享口令 + 无登录 = 所有访客共用一个身份。
这道门是**防蹭不是防攻击**，因此服务器上**不得存放任何真实企业数据**，
全部为模拟数据。

**口令管理**：口令不写在代码里（否则改一次要重新部署），
存服务器配置文件 / 环境变量，提供改口令的命令或独立小页面，PM 自行修改。
改口令的入口用独立的管理口令保护，与访客口令分开。

### 10.3 回答对比调试 ★（真实模式专属）

**光有写权限不够。** 改完文档后靠记忆去比对上次的回答，这没法用。
所以需要一个专门的对比工具：

```
① 维护一组测试问题
   · 内部助手：10 个典型需求（如"订单管理模块退款需求的 PRD"）
   · AI 客服：  10 个典型客户问题（含口语化说法）
        ↓
② 点「跑一遍」→ 生成快照 A
   记录每个问题的：拆解结果 / 召回片段 / 最终回答 / 客服命中率
        ↓
③ 去改东西
   改原始文档 / 调切分参数 / 改 Prompt / 改 Skill / 改同义词表
        ↓
④ 再点「跑一遍」→ 生成快照 B
        ↓
⑤ 快照 A ↔ 快照 B 并排对比
   · 哪些问题的召回片段变了
   · 哪些回答内容变了
   · 客服命中率 / 转人工率的变化
   · 结论：变好、变坏、还是无影响
```

**这个工具同时服务三件事**：

1. 第八章的「重新加工回归验证」
2. 第五章的「Prompt / Skill 改动试跑对比」
3. 第七章的「同义词表效果验证」（命中率 62% → 87% 这类硬指标）

### 10.4 落地页引导

演示项目最大的失败是**访客点进来不知道该看什么就走了**。
落地页必须给一条明确的体验路径：

```
三步看懂这个项目：

① 用「产品经理」身份，输入一个需求，生成一份 PRD
   → 看它引用了哪些企业文档

② 切换成「客服」身份，问同一个问题
   → 看答案怎么变（密级隔离生效了）

③ 切换成「知识管理员」，查看刚才那次回答的召回详情
   → 看它召回了哪些知识片段，以及怎么修
```

## 十一、本期明确不做（边界）

| 不做的 | 原因 |
| --- | --- |
| 真实 OCR（扫描版 PDF 文字识别） | 依赖外部服务，解析失败状态已覆盖这类场景 |
| 真实 Embedding 模型调用 | 用 TF-IDF + 余弦相似度模拟，机制完整可讲；接口预留可替换 |
| 分布式向量数据库 | 用 JSON 文件 + 内存索引模拟，文档量级足够演示 |
| 原文像素级高亮 | 溯源做到「定位章节/页码 + 展示对应原文片段」，见 4.4 |
| 真实工单系统对接（客服转人工） | 转人工动作落到「待人工处理」列表，不对接外部系统 |
| 多租户 | 单企业场景 |
| 移动端 | 桌面端为主 |

> 说明：模拟实现不等于降低设计要求。上面每一项的**接口和数据结构都按真实
> 方案设计**，替换成真实组件时不需要改调用方——这本身也是可讲的设计考量。
