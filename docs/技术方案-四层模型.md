# 技术方案：四层知识模型

> 这份是给代码看的契约文档，不是给 PM 看的。业务需求见 `需求文档.md` 第四、八章。
> 第 8 步实现依据。任何实现偏离本文档，以本文档为准或先改本文档。

## 0. 为什么要重构

现状：`data/documents.json` 是一个扁平数组，每条记录内嵌 `content` 和 `chunks`。

这个结构撑不住 v3 的需求：

| v3 需求 | 扁平结构为什么不行 |
| --- | --- |
| 重新加工先出草稿版本再对比生效 | 没有版本概念，重新加工只能覆盖 |
| 换 Embedding 模型做效果对比 | 向量和切片混在一起，一个切片存不了两份向量 |
| 影响预览「将影响 37 个片段，其中 12 个被引用 45 次」 | 片段没有独立身份，无法被引用统计 |
| 逐层向上溯源 | 层级是嵌套关系，无法从片段反查 |
| 删除文档连带向量失效 | 删了就都没了，但也无法知道影响面 |

## 1. 存储布局

四张独立表，`lib/store.js` 各存一个 JSON 文件：

| 表名 | 文件 | ID 前缀 | 说明 |
| --- | --- | --- | --- |
| `raw_documents` | `data/raw_documents.json` | `raw_` | 第一层 原始文档 |
| `std_documents` | `data/std_documents.json` | `std_` | 第二层 标准化文档 |
| `chunks` | `data/chunks.json` | `chk_` | 第三层 知识片段 |
| `vectors` | `data/vectors.json` | `vec_` | 第四层 向量 |

> `data/documents.json`（旧扁平表）迁移后保留为 `data/documents.legacy.json`，
> 代码不再读取。迁移脚本见第 7 节。

## 2. 层级关系与不变量

```
raw_documents ──1:N──→ std_documents ──1:N──→ chunks ──1:N──→ vectors
                  ↑                                            ↑
            每次重新加工                                每个 Embedding 模型
            产生一个新版本                                  产生一份向量
            只有一个 isCurrent                        同模型下只有一个 isCurrent
```

### 必须始终成立的不变量（测试要逐条锁住）

| # | 不变量 | 违反的后果 |
| --- | --- | --- |
| I1 | 同一 `rawId` 下，`isCurrent === true` 的 std 最多 1 条 | 检索会同时命中两个版本，答案自相矛盾 |
| I2 | 同一 `chunkId` + 同一 `model` 下，`isCurrent === true` 的 vector 最多 1 条 | 同一片段被召回两次，挤掉别的答案 |
| I3 | 每个 std 的 `bizLine`/`securityLevel` 必须等于其 raw 的值 | 权限判据不一致 = 越权 |
| I4 | 每个 chunk / vector 的 `bizLine`/`securityLevel`/`status` 必须等于其 std 的值 | 同上。第 7 步真出过这个 bug |
| I5 | 不存在指向不存在上层记录的孤儿记录 | 溯源断链，影响预览算错 |
| I6 | 只有 `status ∈ {published, need_review}` 且 `isCurrent === true` 的 vector 参与检索 | 未审核内容泄漏 |
| I7 | `raw.currentStdId` 必须等于该 raw 下 `isCurrent` 的 std 的 id，或两者同时为空 | 第二真相源，`impactOf(reprocess, raw, ...)` 的 reprocess 路由依赖它 |

> **I3/I4 是硬性要求，不是优化。** 第 7 步的真实事故：`buildIndex` 白名单拷贝字段时
> 漏了 `status`，而权限过滤对"缺失 status"的处理是"按兼容旧数据放行"，
> 两个各自合理的决定凑一起，整层状态过滤静默失效。
> 因此：**权限判据字段必须每层冗余存储，且创建时强制从上层继承，不接受调用方传入。**

## 3. 字段定义

### 3.1 共同字段（四层都有）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | string | 本层唯一，带层前缀 |
| `bizLine` | string | 权限判据。`trade`/`membership`/`all` |
| `securityLevel` | string | 权限判据。`public`/`internal`/`confidential`/`secret` |
| `status` | string | 见第 4 节状态机 |
| `createdAt` | ISO string | |
| `updatedAt` | ISO string | |

### 3.2 raw_documents（第一层）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `title` | string | 文档名称 |
| `fileName` | string\|null | 原文件名 |
| `fileType` | string | `md`/`docx`/`pdf`/`pptx`/`txt` |
| `fileSize` | number | 字节 |
| `content` | string | 原文全文（**必须保留**，支持重新加工） |
| `knowledgeType` | string | `requirement`/`api`/`test_spec`/`business_rule`/`faq`/`other` |
| `version` | string | 业务版本号，如 `v1.2`（人工填写，与 std 的加工版本无关） |
| `tags` | string[] | |
| `owner` | string\|null | 负责人（复审提醒发给他） |
| `validUntil` | ISO string\|null | 有效时间，到期转 `need_review` |
| `uploadedBy` | string | |
| `currentStdId` | string\|null | 当前生效的标准化文档 ID（冗余，便于快查；不变量 I7） |
| `parseError` | string\|null | 解析失败原因 |
| `legacyId` | string\|null | 旧扁平表（`data/documents.json`）里的原始 id，仅迁移场景写入，非迁移恒为 null。**必要而非画蛇添足**：旧记录允许 `fileName` 为空（手工粘贴内容就没有文件名），没有这个字段迁移判重键会退化成 `|createdAt` 而失效 |

### 3.3 std_documents（第二层）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `rawId` | string | **上层 ID** |
| `procVersion` | number | 加工版本，同 raw 下从 1 递增 |
| `isCurrent` | boolean | 是否当前生效（不变量 I1） |
| `params` | object | **加工参数快照**，见 3.6。没有这个就不知道这版是怎么来的 |
| `content` | string | 标准化后的全文 |
| `sections` | object[] | 章节结构树 `{level, heading, path, startLine, endLine}` |
| `processLog` | object[] | 加工日志 `{step, action, before, after, at}` |
| `qualityScore` | object\|null | 文档级质检结果 `{score, issues[]}` |
| `reviewedBy` / `reviewedAt` / `reviewNote` | | 审核信息 |
| `publishedAt` | ISO string\|null | |

### 3.4 chunks（第三层）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `stdId` | string | **上层 ID** |
| `rawId` | string | 冗余，便于一步回溯到原始文档 |
| `seq` | number | 在 std 内的序号，从 1 |
| `heading` | string\|null | 所属小节标题 |
| `sectionPath` | string[] | 章节路径，如 `['3. 退款流程','3.2 审核时效']` |
| `content` | string | 片段正文 |
| `charCount` | number | |
| `fingerprint` | string | 内容指纹，跨文档去重用 |
| `keywords` | string[] | |
| `qualityScore` | object\|null | 片段级质检 `{score, issues[]}` |
| `embeddingStatus` | string | `pending`/`done`/`failed` |

### 3.5 vectors（第四层）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `chunkId` | string | **上层 ID** |
| `stdId` / `rawId` | string | 冗余，便于跨层查询 |
| `model` | string | 向量模型名，如 `tfidf-v1` |
| `dim` | number | 向量维度 |
| `vec` | number[] | 向量值 |
| `indexName` | string | 所属索引 |
| `isCurrent` | boolean | 同 chunk+model 下唯一（不变量 I2） |

### 3.6 加工参数 params（可调，第八章的核心）

```js
{
  splitMode: 'section' | 'paragraph' | 'fixed',  // 切分粒度
  fixedSize: 400,            // splitMode=fixed 时的字数
  overlap: 50,               // 固定字数模式的重叠字数
  minChunkLength: 30,
  maxChunkLength: 600,
  keepTableStructure: true,  // 表格转 Markdown 而非拉平
  prependHeading: true,      // ★ 把章节标题拼进片段正文，对命中率影响最大
  cleanLevel: {
    stripHeaderFooter: true,
    stripRevision: true,
    mergeShortParagraphs: false,
  },
  dedupThreshold: 1.0,       // 1.0 = 完全相同才算重复
}
```

默认值由 `config.processing` 提供。每个 std 存一份**快照**，
这样"这个版本是用什么参数加工的"永远可查，也才能做新旧参数对比。

## 4. 状态机

### 4.1 raw_documents

```
uploaded ──解析──→ parse_failed ──重试──┐
    │                                   │
    └───────────────────────────────────┘
    │
    ↓
  ready  ←── 一直保持（原始文档本身不参与检索，不需要复杂状态）
    │
    ↓ 删除
 (级联删除)
```

`raw.status ∈ { uploaded, parsing, parse_failed, ready }`

### 4.2 std_documents（**这是真正的业务状态机**）

```
   draft ──质检──→ qc_failed ──修正参数重新加工──→ (新 draft)
     │
     ↓ 提交审核
  pending ──驳回──→ rejected
     │
     ↓ 通过
  approved ──切分+向量化完成+发布──→ published
                                       │
                          ┌────────────┼────────────┐
                          ↓            ↓            ↓
                    有效期到       新版本发布      手动下架
                          ↓            ↓            ↓
                    need_review    archived     archived
                          │
                          └── 复审通过 → published
```

允许的流转（其余一律拒绝，测试要锁）：

| from | to |
| --- | --- |
| `draft` | `qc_failed`, `pending`, `archived` |
| `qc_failed` | `archived` |
| `pending` | `approved`, `rejected`, `draft` |
| `rejected` | `archived` |
| `approved` | `published`, `archived` |
| `published` | `need_review`, `archived` |
| `need_review` | `published`, `archived` |
| `archived` | （终态） |

`draft → archived`（废弃草稿）与 `pending → draft`（撤回送审）是两个日常动作，
v3 初始流转表漏了。补这两条让"草稿写坏了想扔掉"和"送审送早了想撤回"有路可走。

`archived` 保持终态。**版本回滚不是让旧版本复活**，而是
`rollbackToVersion(srcStdId)`：复制 src 的 `content` / `params` / `sections`
创建一个新版本（status=draft，走正常审核发布）。版本号只增不减 —— 审计上
永远能看出当前是第几版、每版活过哪段时间（同 git 用 revert 而不是 reset 的理由）。

**可检索状态**：`published`、`need_review`
（`need_review` 仍可检索，但 AI 答案里要标注「此规则可能已过期」）

### 4.3 chunks / vectors

不独立流转，**始终跟随所属 std 同步**（不变量 I4）。
**任何 std 状态变化都同步下游两层**，不只 publish/archive ——
契约原文只点名了 publish/archive，但 I4 是"始终成立"，只同步两处
会在 `pending`/`rejected` 时破 I4。这是比契约更强的实现，是对的。

## 5. `lib/knowledge-layers.js` API

```js
// ---------- 常量 ----------
LAYERS            // { RAW:'raw', STD:'std', CHUNK:'chunk', VECTOR:'vector' }
RAW_STATUS        // { UPLOADED, PARSING, PARSE_FAILED, READY }
STD_STATUS        // { DRAFT, QC_FAILED, PENDING, REJECTED, APPROVED, PUBLISHED, NEED_REVIEW, ARCHIVED }
RETRIEVABLE       // ['published','need_review']
TRANSITIONS       // { [from]: [to, ...] }

// ---------- 第一层 ----------
createRaw(input)                  // → raw。校验 bizLine/securityLevel/knowledgeType 合法性
markParseFailed(rawId, reason)    // → raw
markReady(rawId)                  // → raw
getRaw(rawId)

// ---------- 第二层 ----------
/**
 * 新建一个标准化版本。
 * - procVersion 自动 = 同 raw 下 max + 1
 * - bizLine/securityLevel 强制从 raw 继承，忽略 input 里的同名字段（不变量 I3）
 * - 初始 status = draft，isCurrent = false（草稿不生效）
 */
createStdVersion(rawId, input)

setStdStatus(stdId, next, meta)   // 按 TRANSITIONS 校验，非法流转 throw 409。
                                 // setStdStatus(x, 'published' | 'archived')
                                 // 转交 publishStd / archiveStd —— 只留一条写路径

/**
 * 让某个 std 版本生效并发布：
 *   1. 同 raw 下其他 isCurrent 的 std → isCurrent=false，且若为 published/need_review 则转 archived
 *   2. 本 std → isCurrent=true, status=published, publishedAt=now
 *   3. 同步其 chunks 与 vectors 的 status（不变量 I4）
 *   4. 更新 raw.currentStdId
 * 保证不变量 I1。
 */
publishStd(stdId)

archiveStd(stdId)                 // std + 下游两层同步 archived
markNeedReview(stdId)             // published → need_review

/**
 * 从历史版本回滚：复制 srcStdId 的 content / params / sections 建新版本（status=draft）。
 * src 本身不动；新版本走正常审核发布流程。
 * 为什么不直接让 src 复活：审计上保留"版本号只增不减"，与 git revert 同理。
 */
rollbackToVersion(srcStdId)

getStd(stdId)
listStdByRaw(rawId)               // 按 procVersion 降序

// ---------- 第三层 ----------
/**
 * 批量创建片段。
 * - 仅当 std 处于 draft / qc_failed / pending / approved 才允许追加
 *   （已发布 / 复审中 / 已驳回 / 已归档 → 409，引导"重新加工出新版"）
 * - bizLine / securityLevel / status 强制从 std 继承（不变量 I4）
 * - rawId 自动从 std 带出，seq 在该 std 内连续递增
 */
createChunks(stdId, chunkInputs)
getChunk(chunkId)
listChunksByStd(stdId)

// ---------- 第四层 ----------
/**
 * 为片段创建向量。
 * - 所属 std 已归档 → 409（终态版本向量永不参与检索，建出来是垃圾）
 * - 所属 std 在 published / need_review → 允许（补建漏向量、换模型重算都是合法运维）
 * - 同 chunkId + 同 model 已有 isCurrent 的向量时，旧的置 false（不变量 I2）
 * - bizLine / securityLevel / status 强制从 chunk 继承
 * - encoding 默认 'dense'，可显式传 'sparse'，非法值抛 400
 */
createVector(chunkId, { model, dim, vec, indexName, encoding? })

/** 批量建向量（单 chunk 多个 model），一次落盘。I2 在批量内去重 */
createVectors(chunkId, [{ model, dim?, vec, indexName?, encoding? }, ...])

/** 跨片段批量建向量；items 支持两种形式：
 *    [{ chunkId, vectors: [...] }]   —— 一个 chunk 多个向量
 *    [{ chunkId, model, vec, ... }]  —— 一个 chunk 一个向量（直接一条 record） */
createVectorsBatch(items)

listVectorsByChunk(chunkId)

/** 参与检索的向量：status ∈ RETRIEVABLE 且 isCurrent（不变量 I6） */
listRetrievableVectors()

// ---------- 级联 ----------
/**
 * 删除原始文档 → 连带删除其所有 std / chunk / vector。返回删除计数
 * 返回结构: { rawCount, stdCount, chunkCount, vectorCount }
 * 与 impactOf 的字段对齐，方便"预览的数 == 真删的数"做断言
 */
deleteRawCascade(rawId)

/** 删除某个 std 版本 → 连带其 chunk / vector。返回 { stdCount, chunkCount, vectorCount } */
deleteStdCascade(stdId)

// ---------- 完整性自检 ----------
/** 检查全部不变量（含 I7），返回违反项列表。用于测试与运维自检 */
checkInvariants()

// ---------- 便捷读取（别名） ----------
listRaws()                        // listAll(RAW)
listStds()                        // listAll(STD)
listChunks()                      // listAll(CHUNK)
listVectors()                     // listAll(VECTOR)
```

### 关键实现约束

1. **权限判据字段一律由上层继承，不接受调用方传入。**
   `createStdVersion` / `createChunks` / `createVector` 收到 input 里带
   `bizLine`/`securityLevel`/`status` 时**直接忽略并覆盖**，不报错（调用方可能顺手传了）。
   这是不变量 I3/I4 的实现方式——不靠调用方自觉。

2. **所有写操作走 `lib/store.js`**，不直接读写文件。注意 store 有模块级缓存。

3. **状态流转只能通过 `setStdStatus` / `publishStd` / `archiveStd`**，
   不提供直接改 status 的口子。

## 6. `lib/traceability.js` API

```js
/** 向上追溯一层。raw → null */
traceUp(layer, id)          // → { layer, record } | null

/** 向下展开一层。vector → [] */
traceDown(layer, id)        // → { layer, records[] }

/** 完整面包屑，从 raw 到当前层 */
breadcrumb(layer, id)       // → [{layer, id, label}, ...]

/** 完整链条：给定任意层任意 id，返回它所在的整条链 */
fullChain(layer, id)        // → { raw, std, chunk, vector } 各字段可能为 null 或数组

/**
 * 影响预览。第八章的核心，危险操作前必须调用。
 * action ∈ 'reprocess' | 'delete' | 'archive'
 * → {
 *     action, targetLayer, targetId, destructive: boolean,
 *     stdCount, chunkCount, vectorCount,
 *     citedChunkCount,     // 其中被 AI 引用过的片段数
 *     citationCount,       // 总引用次数
 *     recentDays,          // 引用统计的时间窗口
 *     warnings: string[],
 *   }
 */
impactOf(action, layer, id, opts)

/** 孤儿检测：指向不存在上层的记录 */findOrphans()
```

**引用统计的数据来源**：第 14 步的检索快照表 `retrieval_snapshots`。
第 8 步实现时该表还不存在——**必须优雅降级**：
表不存在或为空时 `citedChunkCount`/`citationCount` 返回 0，
并在 `warnings` 里加一条"引用统计数据暂不可用"。
不能因为表不存在就抛错。

**`impactOf` 行为约定**（实现期与代码一致）：
- `reprocess` 影响的范围 = 该 raw 下当前生效版本（依赖 `currentStdId`，不变量 I7）。
  `delete` / `archive` 影响的范围 = 该 raw 全部版本。
- `destructive` = `delete`/`archive` 为 true，`reprocess` 为 false。
- `recentDays` 默认 7（与需求文档第八章「过去 7 天被引用 45 次」对齐）。
  传 0 / 负数 / 非数字 / NaN 一律抛 400（不能静默变默认值，也不能把窗口甩到未来 → 统计恒为 0）。
- 引用次数定义：被 affected 命中的快照行内命中片段数（每行内同一 chunkId 重复只算一次；
  一行多个不同 chunkId 命中各算 1）。

## 7. 迁移

`scripts/migrate-to-layers.js`：

```
读 data/documents.json（旧扁平表）
  ↓
每条旧记录 →
    1 条 raw_documents   （content / bizLine / securityLevel / tags / uploadedBy 直接搬）
    1 条 std_documents   （procVersion=1, isCurrent=按旧 status 决定, params=config 默认值）
    N 条 chunks          （从旧记录的 chunks 数组搬，补 seq / stdId / rawId / 继承权限字段）
    0 条 vectors         （向量在第 12 步重建，迁移时不生成）
  ↓
旧 status 映射：
    approved → std.status = published, isCurrent = true
    pending  → std.status = pending,   isCurrent = false
    rejected → std.status = rejected,  isCurrent = false
  ↓
data/documents.json → 重命名为 data/documents.legacy.json
  ↓
跑 checkInvariants()，有违反项则回滚并报错
```

迁移脚本必须**幂等**：重复执行不产生重复数据（按 raw 的 fileName+createdAt 判重；fileName 为空时退回 legacyId）。

**显式闸门**：`migrate({ confirmed: true })` 才真的执行；默认 `require('migrate-to-layers')` 或
直接 `node scripts/migrate-to-layers.js`（无 `CONFIRM_MIGRATE=1`）都只打警告不动手。
原因：当前的 `lib/documents.js` / `routes/*` 还全在读旧的 `documents` 表，
跑迁移会让运行中的应用立刻变成空知识库。闸门在下一批把上传/审核/检索
接到新结构上后拆。

**回滚粒度**：raw 一创建成功立刻登记到 `createdRawIds`，后续 `createStdVersion` /
`createChunks` / 状态流转任一步抛错都会带上这条 raw 一起回滚。
不这么做的话，半截 raw 留在表里判重键撞上旧记录，重试时这条被 skip，
std 永远停在 draft、片段永远为 0，迁移会"成功"并把旧表改名 —— 静默丢数据。

## 10. 第 12 步的存储决策

### 实测数据（本步刚完成，2026-08-12）

`mock-data/documents` 下 13 个文件，标量化后：

| 指标 | 数值 |
| --- | --- |
| 片段数 | 373 |
| 词表维度 | **11093**（远超"几千维"的预期） |
| 稠密向量 JSON 大小（缩进 2） | ≈ 100 MB / 文件 |
| 累计写盘（每条 createVector 一次全表覆写） | 十几 GB |
| 耗时 | **分钟级** |

### 决策

**向量必须用稀疏编码**，不能用稠密。理由：

1. 单条 11093 维的稠密向量大部分维是 0（TF-IDF 词表里大多数词不在这一段里），
   稀疏表示 `{idx: [...], val: [...]}` 体积只有稠密的 1/50 ~ 1/100
2. `vector-store.search` 里 cosine 是 O(min(a.length, b.length)) 的全量内积，
   改成稀疏后可以只对非零维做点积，**单次查询也快 10× ~ 100×**
3. JSON 不缩进已经做了（见 [第 1 节](#1-存储布局)），
   解决了一半问题，剩下的一半靠编码方式

**本步的预备**：
- 向量记录新增 `encoding: 'dense' | 'sparse'` 字段（默认 `dense`）
- 提供 `createVectors` / `createVectorsBatch` 批量接口（见 [第 5 节](#5-libknowledge-layersjs-api)），
  一次落盘替代逐条建
- `vectors.json` 不缩进

**第 12 步落地**：
- `lib/vector-store.vectorize` 改为产出 `{idx: number[], val: number[]}` 稀疏形式
- `search` / `rerank` 改写以消费稀疏向量
- 现有 vectors 表是空的（第 8 步还没建过向量），切换零成本
- `dim` 字段保留，记录全维度（即 11093）便于切换编码时回退

> 选型对比：为什么不直接上 sqlite / faiss？本项目是流程演示，
> 存 JSON 是因为能直接打开看和改，演示级并发下足够。
> 等真上生产再换，那是另一个工程。
